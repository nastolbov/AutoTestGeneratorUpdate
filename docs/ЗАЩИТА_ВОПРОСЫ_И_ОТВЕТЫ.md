# Защита ВКР — вопросы комиссии и подробные ответы

Генератор автотестов веб-интерфейса по XML-метамодели (платформа E3Core, АИС «ГСК»).
Технологии: **Java 17, JavaFX, StAX, Selenium WebDriver, JUnit + Maven Surefire, SQLite**.
Паттерны: **Page Object, DAO, Factory, классификатор-стратегия**.

---

## Карта системы (держите перед глазами)

```
            ВХОД                ОБРАБОТКА                       ВЫХОД
   ┌──────────────────┐   ┌───────────────────────┐   ┌────────────────────┐
   │  XML-метамодель  │   │  parser  → model      │   │ Java-классы тестов │
   │  системы (E3Core)│──▶│  (StAX)    (объекты)  │──▶│ (Selenium + JUnit) │
   └──────────────────┘   │           │           │   └─────────┬──────────┘
                          │   EntityClassifier    │             │ mvn test
                          │  PRIMARY/CHILD/REF     │             ▼
                          │           │           │   ┌────────────────────┐
                          │   generator (пишет код)│   │   TestRunner       │
                          └───────────┬───────────┘   │ запускает Chrome   │
                                      │               └─────────┬──────────┘
                                      ▼                         ▼
                               ┌────────────┐         ┌────────────────────┐
                               │  SQLite    │◀────────│ отчёты HTML/CSV +   │
                               │ (история)  │         │ скриншоты           │
                               └────────────┘         └────────────────────┘
```

Поток данных одной фразой: **XML → объектная модель → классификация → генерация кода → запуск в браузере → отчёты и история.**

# 1. Актуальность и постановка задачи

**1. В чём проблема, которую решает работа? Почему ручные автотесты — дорого?**
Ручное написание UI-автотестов трудоёмко: для каждой сущности нужно вручную описать формы, поля, шаги CRUD, селекторы. На систему из десятков сущностей это сотни почти одинаковых тестов. При этом вся информация о структуре форм **уже есть в XML-метамодели** платформы. Моя работа автоматически превращает эту метамодель в готовые тесты — человек не пишет рутинный код.

**2. Кто заказчик / где применяется?**
Системы на платформе E3Core (пример — АИС «Гаражно-строительные кооперативы»). Любая подсистема платформы описывается XML-моделью того же формата, поэтому генератор применим к семейству таких систем, а не к одной.

**3. Цель и задачи.**
*Цель* — сократить трудозатраты на создание автотестов веб-интерфейса за счёт генерации из метамодели.
*Задачи*: (1) разобрать XML в объектную модель; (2) классифицировать сущности по типу тестируемого сценария; (3) сгенерировать компилируемые Selenium-тесты; (4) запускать их и собирать отчёты; (5) хранить историю прогонов.

**4. Объект и предмет.**
*Объект* — процесс автоматизированного тестирования веб-приложений. *Предмет* — методы генерации тестов из формального описания (метамодели) интерфейса.

**5. Чем подход лучше «написать один раз руками»?**
При изменении модели (добавили поле/сущность) тесты **перегенерируются за секунды**, а не правятся вручную. Снимается человеческий фактор (опечатки в селекторах), обеспечивается единый стиль.

**6. Сколько экономит?**
Аргумент для защиты: на старте программа сообщает `Сгенерировано тестовых классов: 19`. Вручную один CRUD-класс с Page Object — это часы. 19 классов генерируются мгновенно. Назовите консервативную оценку (например, 1–2 часа на класс вручную → десятки человеко-часов на подсистему).

**7. Почему UI, а не API/юнит?**
UI-тесты проверяют систему целиком глазами пользователя (формы, сохранение, навигация). Именно UI-сценарии самые дорогие в ручной автоматизации — поэтому выигрыш от генерации тут максимален. Метамодель описывает именно представления (формы, гриды, поиски).

# 2. Архитектура и технологии

**8. Общая архитектура (модули).**
```
ru.autotestgen
 ├── parser     — чтение XML (StAX): XmlModelParser, EntityParser, SearchParser…
 ├── model      — объектная модель: EntityObject, Property, PropertyGroup, Search,
 │               + EntityClassifier (логика PRIMARY/CHILD/REFERENCE)
 ├── generator  — генерация и запуск: TestGenerator, TestClassWriter,
 │               PageObjectWriter, TestDataFactory, TestRunner, RunReportWriter
 ├── data       — SQLite: DatabaseConnection, SchemaInitializer, *Dao
 ├── common     — утилиты: Transliterator, JavaFileWriter, ParserException
 └── ui         — JavaFX: Launcher, App, MainController (+ fxml/main.fxml)
```
Чёткое разделение слоёв: парсинг → модель → генерация → запуск → данные → интерфейс.

**9. Почему Java? Почему JavaFX?**
Java — потому что Selenium и экосистема тестирования (JUnit, Maven Surefire) для неё родные, и сами тесты получаются на Java. JavaFX — кроссплатформенный десктоп-GUI без браузера/сервера; приложение запускается локально у тестировщика.

**10. Зачем `Launcher` отдельно от `App`?** *(каверзный, любят спрашивать)*
`App extends Application` (JavaFX). Если точкой входа jar сделать класс-наследник `Application`, JavaFX из обычного «толстого» jar падает с «JavaFX runtime components are missing». `Launcher` **не** наследует `Application`, он просто вызывает `App.main()` — это штатный обход проблемы.
```java
public class Launcher {            // не наследует Application
    public static void main(String[] args) {
        App.main(args);            // а уже App extends Application
    }
}
```

**11. Какие паттерны проектирования?**
- **Page Object** — для каждой сущности генерируется класс-страница (`PageObjectWriter`), инкапсулирующий селекторы и действия.
- **DAO** — доступ к БД (`ReportDao`, `TestRunDao`, `TestCaseDao`).
- **Factory** — `TestDataFactory` создаёт тестовые значения по типу поля.
- **Strategy/классификатор** — `EntityClassifier` выбирает сценарий генерации по типу сущности.

**12. Что такое Page Object и зачем?**
Шаблон: страница/форма приложения = отдельный класс с методами-действиями и селекторами. Тест не знает CSS-селекторов — он зовёт методы страницы. Если интерфейс меняется — правится один Page Object, а не десятки тестов. У меня его генерирует `PageObjectWriter`.

**13. Почему StAX, а не DOM/SAX?**
DOM грузит весь документ в память (модель может быть большой). SAX — событийный, но неудобно «вытаскивать поддеревья». **StAX** — потоковый «pull»-парсер: читаю по курсору, контролирую, когда заходить внутрь элемента, память не раздувается. Утилиты — `StaxUtils`.

**14. Зачем SQLite, а не файлы/Excel?**
Нужна история прогонов с возможностью запросов (последний прогон, динамика). SQLite — встроенная БД-файл, без сервера, с SQL. Идеально для локального десктоп-приложения.

**15. Схема БД.**
```
test_run (1) ──────< (N) test_case
 id  PK                 id  PK
 run_date               run_id  FK→test_run.id
 xml_file               class_name
 base_url               method_name
 total/passed/          passed (0/1)
 failed/skipped         failure_msg
 duration_ms            duration_ms
```
Один прогон (`test_run`) → много результатов по методам (`test_case`). Реальный DDL (`SchemaInitializer`):
```sql
CREATE TABLE IF NOT EXISTS test_run (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  run_date TEXT NOT NULL, xml_file TEXT NOT NULL, base_url TEXT NOT NULL,
  total INTEGER, passed INTEGER, failed INTEGER, skipped INTEGER, duration_ms INTEGER);

CREATE TABLE IF NOT EXISTS test_case (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id INTEGER NOT NULL REFERENCES test_run(id),
  class_name TEXT, method_name TEXT,
  passed INTEGER, failure_msg TEXT, duration_ms INTEGER);
```

**16. Что такое DAO и какие есть?**
DAO (Data Access Object) — слой, прячущий SQL от остальной программы. `TestRunDao` сохраняет прогон, `TestCaseDao` — результаты методов, `ReportDao` — выборки для отчётов. Остальной код работает с объектами, а не с SQL.

# 3. Парсинг XML и модель

**17. Что за входной XML, откуда?**
Это **метамодель подсистемы** платформы E3Core — формальное описание сущностей, их свойств, форм (карточка/грид), операций и поисков. Выгружается из самой платформы. Пример: `5EA195D102D1_Stc` (АИС ГСК).

**18. Объектная модель.**
```
AppModel
 └── List<EntityObject>           // сущность
      ├── guid, name, featureName
      ├── List<PropertyGroup>     // группы свойств = вкладки/формы
      │     ├── stereoType: "Card" | "Grid" | …
      │     └── List<Property>    // поле: attrName, attrType, mask, stereoType
      ├── List<Operation>         // CRUD-операции (+ Modifier: I/U/D)
      ├── List<Association>       // связи (в т.ч. addFromTree)
      └── List<Search>            // поиски с параметрами
```
Каждый XML-элемент имеет свой класс модели — код работает с типобезопасными объектами, а не со строками.

**19. Пространства имён.**
Вынесены в `XmlNamespaces`, чтобы префиксы/URI не были «магическими строками» по коду — один источник правды, легко поддерживать при смене версии формата.

**20. Что при битом/неполном XML?**
Парсеры бросают `ParserException` с понятным сообщением; UI показывает ошибку, а не падает. На старте печатается `XML разобран успешно. Найдено сущностей: 19, поисков: 17` — то есть результат парсинга виден пользователю.

**21. Транслитерация — зачем?**
Имена сущностей русские («ГСК/ОГСК»), а имя Java-класса не может быть кириллицей и не должно содержать `/`. `Transliterator` превращает «ГСК/ОГСК» → `GSKOGSK`, отсюда класс `GSKOGSKTest` (видно в логе прогона).

**22. Гарантия корректных имён классов?**
Да: транслитерация + очистка недопустимых символов + приведение к виду идентификатора Java. Поэтому из любой кириллицы получается валидное имя класса.

# 4. Классификация сущностей (ядро «интеллекта»)

**23. Как программа решает, что генерировать?**
Этим занимается `EntityClassifier`. Он смотрит на **структуру** сущности (а не на имя) и относит её к одному из типов, для каждого — свой сценарий тестов.

**24. PRIMARY / CHILD / без тестов — по какому признаку?**
```
                 ┌─────────────────────────────────────────┐
 EntityObject ──▶│ есть grid-вкладка в другой сущности?     │── да ─▶ CHILD
                 │ (имя совпадает с Grid внутри родителя)   │
                 └───────────────┬─────────────────────────┘
                                 │ нет
                 ┌───────────────▼─────────────────────────┐
                 │ узел дерева (addFromTree) + свой CRUD?    │── да ─▶ CHILD (tree)
                 └───────────────┬─────────────────────────┘
                                 │ нет
                 ┌───────────────▼─────────────────────────┐
                 │ справочник? (V_S_*, поиск без параметров │── да ─▶ REFERENCE_DICTIONARY
                 │ или цель только FK-пикера)               │        (без отд. класса)
                 └───────────────┬─────────────────────────┘
                                 │ нет
                                 ▼
                              PRIMARY  (пункт меню + CRUD + свои поиски)
```
Реальный код решающего ядра:
```java
public static Classification classify(EntityObject entity, AppModel model) {
    Classification childResult = findParentGrid(entity, model);     // grid-вкладка → CHILD
    if (childResult != null) return childResult;

    EntityObject treeParent = findTreeParent(entity, model);        // узел дерева
    if (treeParent != null && entity.hasCrudOperations())
        return new Classification(EntityKind.CHILD, "tree node …", treeParent, null);

    String dictReason = isReferenceDictionary(entity, model);       // справочник
    if (dictReason != null) return new Classification(EntityKind.REFERENCE_DICTIONARY, dictReason);
    …
    return new Classification(EntityKind.PRIMARY, "has menu entry, CRUD and own searches");
}
```
«Без тестов» в логе (`без тестов=8`) — это REFERENCE_DICTIONARY и недостижимые сущности: для них отдельный CRUD-класс не нужен (они проверяются косвенно через FK-пикеры родителей).

**25. Почему по структуре, а не по именам?** *(ключевой вопрос новизны)*
Имена меняются от подсистемы к подсистеме и от языка. А **структура метаописания одинакова** для всей платформы: тип группы свойств (`Card` vs `Grid`), наличие `<Operation><Modifier>`, флаг `addFromTree`, параметры поиска. Поэтому правило «грид-группа ⇒ inline-CRUD; карточка с операциями ⇒ модальный CRUD; узел дерева ⇒ CRUD из дерева; нет модификаторов ⇒ только проверка наличия» работает на **любой** новой XML. Это и есть «шаблонность».

**26. Модальный CRUD vs inline-грид vs карточка-пикер — как различаю?**
По `stereoType` группы свойств и контексту:
- **Карточка (`Card`) с операциями** → модальная форма: открыть → заполнить → «Готово».
- **Грид (`Grid`)** → inline: «Редактирование → Добавить» → правка ячеек → «Сохранить изменения».
- **Справочник** → не отдельный CRUD, а выбор через FK-пикер в родителе.

**27. Как поведёт себя на НОВОЙ XML? Это правда универсально?** *(топят часто)*
Да, потому что классификация и выбор сценария завязаны на структуру, а не на конкретные сущности ГСК. Я готов **продемонстрировать вживую**: подставить XML другой подсистемы — программа разберёт её, классифицирует и сгенерирует тесты тем же кодом. Честное ограничение: платформа должна быть та же (E3Core), формат метамодели — тот же.

**28. Откуда уверенность, что классификация верна?**
Я сверял результат с официальной документацией платформы и инструкцией пользователя (конспект — `docs/SYSTEM_NOTES.md`): для каждой сущности АИС ГСК зафиксирован реальный UI-флоу (модалка/inline/дерево) и сопоставлен с тем, что выбирает классификатор.

# 5. Генерация тестов

**29. Какие типы тестов генерируются?**
`testFieldsPresent` (поля формы на месте), `testCreate`, `testUpdate`, `testDelete` — видно прямо в фильтре прогона: `GSKOGSKTest#testFieldsPresent+testCreate+testUpdate+testDelete`.

**30. Структура сгенерированного класса.**
```
BaseTest            — общий каркас: @BeforeEach initDriver(), @AfterEach
   ▲                  (инициализация WebDriver, логин)
   │ extends
GSKOGSKTest         — @Test testFieldsPresent / testCreate / testUpdate / testDelete
   │ использует
GSKOGSKPage         — Page Object: селекторы и действия конкретной формы
SharedDriver        — единый Chrome на прогон + performLogin()
```
`initDriver()` поднимает драйвер и логинится один раз, тесты переиспользуют сессию.

**31. Как формируются тестовые данные?**
`TestDataFactory.generateValue(Property)` — по типу поля и **маске из XML**:
```java
String mask = property.getMask();
if (mask != null && !mask.isEmpty()) return generateFromMask(mask);   // уважаем маску
return switch (property.getAttrType()) {
    case DECIMAL  -> String.valueOf(100 + RND.nextInt(900));
    case DATE     -> todayMsk();
    case DATETIME -> nowMskMinus10();                 // чуть в прошлом — валидаторы не любят будущее
    case STRING   -> "Test_" + property.getAttrName();
};
```
`Random` с **фиксированным зерном 42** — значения воспроизводимы (один и тот же прогон даёт те же данные).

**32. «Красный = изменённое поле».**
Платформа подсвечивает несохранённые правки красным; сохранение — «Редактирование → Сохранить изменения». Тест update вводит значение, проверяет, что поле стало «грязным», и жмёт сохранить — это надёжный признак, что правка применилась.

**33. Обязательные поля, маски, справочники, даты.**
- `*` (обязательные) — заполняются всегда.
- Маски — через `generateFromMask`.
- Справочники/FK (`stereoType` = `Directory`/`Ref`) — `generateValue` возвращает `null`, такие поля заполняются через пикер отдельно.
- Даты — корректный формат `dd.MM.yyyy`, время — МСК минус 10 минут.

**34. Что для read-only подсистем?**
Если у сущности нет `<Operation><Modifier>` (нет I/U/D) — генерируется только проверка наличия полей/грида, без create/update/delete.

**35. Почему часть сущностей «без тестов» — баг?**
Нет, это норма: справочники и недостижимые из меню сущности не требуют отдельного класса. Часть «оставшихся skip» у дочерних grid-вкладок — это известное ограничение (см. вопрос 59), оно осознано и описано в роадмапе.

# 6. Запуск тестов и Selenium

**36. Как запускаются тесты?**
`TestRunner` вызывает `mvn test` в каталоге сгенерированного проекта и читает вывод в реальном времени:
```java
List<String> cmd = new ArrayList<>();
cmd.add(mvnCommand);          // абсолютный путь к mvn (см. вопрос 40)
cmd.add("test");
if (testFilter != null) { cmd.add("-Dtest=" + testFilter); cmd.add("-DfailIfNoTests=false"); }
if (fastMode) { cmd.add("-DforkCount=1"); cmd.add("-Dheadless=true"); }
ProcessBuilder pb = new ProcessBuilder(cmd);
pb.redirectErrorStream(true);
pb.directory(projectDir.toFile());
```

**37. Headless и «быстрый режим».**
Headless — браузер без видимого окна (`-Dheadless=true`), быстрее и без мельтешения. «Скрыть визуальную работу браузера» в UI = этот режим.

**38. Почему `forkCount=1`?**
Один браузер за раз. Несколько параллельных Chrome под одним логином ломали сохранение: гонки правок одной сущности и потеря фокуса у клавиатуры. Поэтому в быстром режиме форк один.

**39. Авторизация.**
`SharedDriver.performLogin()` открывает базовый URL и логинится один раз на весь прогон — тесты не логинятся каждый раз заново.

**40. Что если Maven/Chrome не установлены?** *(вы это чинили на демо)*
Для Maven сделан надёжный поиск, т.к. GUI-приложение на macOS наследует урезанный PATH без Homebrew:
```java
private String resolveSystemMaven(String mvnExe, boolean isWindows) {
    // 1) MAVEN_HOME / M2_HOME
    // 2) типичные пути: /opt/homebrew/bin/mvn, /usr/local/bin/mvn, SDKMAN, Program Files\Apache\maven
    // 3) логин-шелл: command -v mvn  /  where mvn
    // 4) иначе — голое имя (вдруг PATH всё-таки содержит mvn)
}
```
Chrome нужен установленный; драйвер подбирается Selenium-ом автоматически.

**41. Ошибка `net::ERR_CONNECTION_CLOSED` — это дефект программы?** *(после провала демо)*
Нет. Браузер запустился (`chrome=150…`), Maven нашёлся, тесты стартовали — то есть **генератор отработал полностью**. Падение произошло на шаге `driver.get(https://rrpo.cmirit.ru/E3Core)` — тестируемый стенд был недоступен (лёг / нужен VPN). Это среда исполнения, а не код.

**42. Как отличить баг системы от проблемы среды?**
По стадии и типу ошибки: сетевые (`ERR_CONNECTION_CLOSED`, таймаут на `get`) и отсутствие драйвера — это среда; а вот «поле не сохранилось», «элемент не найден на форме», «счётчик записей не вырос» — это дефекты тестируемой системы. В отчёте видно метод и сообщение.

# 7. Отчётность и хранение

**43. Какие отчёты?**
- **HTML v5 «с фотолетописью»** (`RunReportWriter`) — наглядный, со скриншотами шагов.
- **Surefire HTML** — стандартный отчёт Maven.
- **CSV** — для выгрузки/таблиц.
Пути печатаются после прогона (`run-report.html`, `surefire-report.html`, `run-report.csv`).

**44. «Фотолетопись» / скриншоты.**
Скриншоты ключевых шагов (и особенно падений) складываются в `target/screenshots/` и привязываются к тест-кейсам по имени файла (`linkScreenshots`) — в HTML видно, что было на экране.

**45. Зачем история прогонов в БД?**
Чтобы видеть динамику: что падало раньше, стабильность, сравнение прогонов. Хранится в `test_run`/`test_case`.

**46. Как парсятся результаты Surefire?**
`parseSurefireReports` читает XML-отчёты Surefire из `target/surefire-reports`, достаёт по каждому методу статус/время/сообщение об ошибке и складывает в `TestRunResult` → затем в БД и отчёты.

# 8. Качество и тестирование самого генератора

**47. Как вы тестировали сам генератор?** *(очень частый и опасный вопрос)*
Несколько уровней: (1) **проверка результата генерации** — сгенерированный проект компилируется и запускается через Maven (если бы код был некорректен, `mvn test` не собрал бы проект); (2) **сверка классификации** с документацией платформы (`SYSTEM_NOTES.md`) — для каждой сущности АИС ГСК зафиксирован эталонный флоу; (3) **прогон на реальной модели** (19 сущностей, 17 поисков) с разбором отчётов.
> Честно: автоматических юнит-тестов на парсер/классификатор пока немного — это первый пункт «что доработать» (см. вопрос 60). Назовите это зоной развития, а не скрывайте.

**48. Как убеждаетесь, что сгенерированный код компилируется?**
Он собирается реальным Maven с JUnit — компиляция самого проекта тестов является проверкой. Имена приводятся к валидным Java-идентификаторам транслитерацией.

**49. Покрытие и граничные случаи.**
Граничные: сущности без операций (read-only), кириллические имена с `/`, грид-вкладки, узлы дерева, справочники-FK. Каждый случай покрыт отдельной веткой классификатора.

**50. Что при изменении интерфейса системы — тесты протухнут?**
Селекторы инкапсулированы в Page Object; при смене модели тесты **перегенерируются** заново. Если меняется сама платформа (вёрстка/идентификаторы) — правится шаблон генерации в одном месте, а не каждый тест.

# 9. Развёртывание и кроссплатформенность

**51. Как запускается приложение? Почему «толстый» jar?**
Maven-shade собирает один исполняемый jar (`AutoTestGenerator.jar`) со всеми зависимостями — запуск `java -jar` без установки библиотек. Точка входа — `Launcher` (вопрос 10).

**52. Зачем разделять нативные библиотеки JavaFX по ОС?** *(реальная проблема, которую решили на защите)*
JavaFX содержит **нативные** библиотеки под каждую ОС/архитектуру: Windows `.dll`, Linux `.so`, macOS `.dylib`. Причём для Mac их две несовместимые: Intel (`x86_64`) и Apple Silicon (`arm64`, classifier `mac-aarch64`). Имена файлов у них одинаковые, в один jar обе mac-версии не помещаются — побеждала Intel, и на MacBook (arm64) была ошибка `incompatible architecture … need 'arm64'`. Решение в `pom.xml`: оставить `win` + `mac-aarch64` (+ Linux авто), убрать Intel-mac.
```xml
<dependency> <artifactId>javafx-graphics</artifactId> <classifier>win</classifier> </dependency>
<dependency> <artifactId>javafx-graphics</artifactId> <classifier>mac-aarch64</classifier> </dependency>
<!-- 'mac' (Intel) НЕ добавляем: .dylib те же имена, конфликтуют в одном jar -->
```

**53. Что нужно установить пользователю?**
Java 17+ (для запуска jar), Maven и Chrome (для прогона сгенерированных тестов). Для раздачи «без установок» — сборка со встроенными JDK/Maven через jpackage.

**54. «Один клик»?**
- Windows: двойной клик по `ЗАПУСТИТЬ.bat` (запуск `javaw -jar`, без консоли) или сборка `.exe` через jpackage.
- macOS: сборка `AutoTestGenerator.app` (`СОБРАТЬ_ПРИЛОЖЕНИЕ_MAC.command`) — двойной клик по иконке.

# 10. Сравнение с аналогами и новизна

**55. Чем отличается от Selenium IDE / Katalon / Playwright Codegen?**
Те работают по принципу **record & playback** — записывают действия человека. Мой генератор ничего не записывает: он **выводит тесты из формальной метамодели**, без ручного прокликивания. Покрытие определяется моделью, а не тем, что успел нажать тестировщик.

**56. Научная/практическая новизна.**
Генерация тестов **из метамодели предметной области** конкретной платформы с автоматической классификацией сценариев (модалка/inline/дерево/справочник) по структуре описания. Это model-based testing, адаптированный под E3Core.

**57. Почему не взять готовый инструмент?**
Готовые не знают семантики платформы (что «красный = грязное», что грид редактируется inline, что справочник выбирается пикером). Мой генератор кодирует эти правила и потому делает осмысленные CRUD-тесты, а не слепой клик-реплей.

**58. Только E3Core или любая система?**
Подход универсален для систем с формальной метамоделью интерфейса. Конкретная реализация заточена под формат метамодели E3Core; перенос на другую платформу = адаптация парсера и шаблонов.

# 11. Ограничения и развитие

**59. Известные ограничения.** *(честно — у вас они описаны)*
Из `SYSTEM_NOTES.md`: (1) дочерние **grid-вкладки** (Документы/Приглашённые/Участники) редактируются inline, а генератор частично ждёт модалку → часть skip; (2) тонкость классификации «Должностные лица» (список) vs «Должностное лицо» (карточка); (3) «логическое изменение» требует сначала проставить новый НДЗ — пока не делается. Это осознанный роадмап точности.

**60. Что доработать при наличии времени?**
Юнит-тесты на парсер/классификатор; inline-CRUD для всех child-grid; CRUD «Повестки» через узел дерева; поддержка логического изменения; сборка со встроенным Maven для раздачи «в один клик».

**61. Масштабируемость на сотни сущностей?**
Парсер потоковый (StAX), генерация линейна по числу сущностей, прогон ограничен только браузером (`forkCount=1` сознательно). Сотни классов сгенерируются; узкое место — время прогона в браузере, а не генерация.

**62. Другие браузеры?**
Сейчас Chrome. Архитектурно — вопрос настройки WebDriver в `SharedDriver`; Selenium поддерживает Firefox/Edge, добавляется конфигом.

# 12. Каверзные / «на засыпку»

**63. Подсуньте другую XML — что будет?**
Программа разберёт её тем же `XmlModelParser`, классифицирует `EntityClassifier`-ом и сгенерирует тесты. Готов показать вживую (нужен валидный XML формата E3Core).

**64. Что генерируется, а что написано руками заранее?**
Руками — **шаблоны** каркаса (`BaseTest`, `SharedDriver`, структура Page Object) и логика генератора. Генерируется — конкретные классы тестов и страниц под каждую сущность модели (имена, поля, шаги, селекторы, данные).

**65. Где ваш вклад, а где библиотеки?**
Библиотеки (Selenium, JUnit, JavaFX, SQLite-JDBC) — инструменты. Мой вклад: парсинг метамодели, **классификатор сценариев**, генерация компилируемого кода тестов и Page Object, раннер с отчётами и историей, кроссплатформенная упаковка.

**66. Прошедший тест доказывает, что система работает?**
Нет. Тест подтверждает только проверенный сценарий на проверенных данных. Зелёный прогон = «эти CRUD-сценарии для этих сущностей отработали», а не «в системе нет ошибок».

**67. Почему 0 из 2 прошло на демо — не проверяли заранее?** *(держите ответ наготове)*
Программа отработала корректно: сгенерировала тесты, нашла Maven, подняла Chrome. Тесты упали на подключении к тестовому стенду `rrpo.cmirit.ru` — он в этот момент был недоступен (`ERR_CONNECTION_CLOSED`, нужен доступ к сети стенда/VPN). Это внешняя среда, а не дефект генератора; на доступном стенде сценарии проходят.
