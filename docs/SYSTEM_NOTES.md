# Конспект по тестируемой системе (E3Core / АИС «ГСК») — для генератора тестов

Источники: «E3Core. Руководство оператора» (платформа, generic) + «Инструкция пользователя
АИС ГСК» (конкретные флоу) + XML-модель `5EA195D102D1_Stc`.

## Платформа E3Core (generic — справедливо для ЛЮБОЙ модели/XML)
- **ППС** = подсистема (subsystem). ППС-ведения (CRUD) vs ППС-подписчик (read-only).
- **Браузер объектов**: дерево объектов → список групп свойств → группа свойств (справа внизу).
- **Группа свойств (PropertyGroup)** бывает типов, каждая на своей вкладке:
  - **Карточка** (Card): атрибут=значение; FK/справочные поля имеют кнопки «перейти по ссылке /
    найти объект (пикер) / очистить». Внизу панель: **«Редактирование»** (меню операций),
    **«Обновить»**, «Печать».
  - **Табличное представление / Грид**: множество объектов таблицей; кнопка **«Редактирование»**
    (операции), пагинация: первая/пред/след/последняя, **«Обновить» (перезагружает данные)**,
    «Печать». Справа — **общее число записей** (наш счётчик create/update!).
  - Отчёты / Пространственные данные / График.
- **Поиск**: дерево поисков → параметры → «Выполнить запрос». Параметр «Отображение
  результата»: `через поисковую систему` (окно результатов, двойной клик грузит в дерево) или
  `через модуль системы` (всё грузится в дерево объектов). Результаты пагинируются.
- **Изменённые значения выделяются КРАСНЫМ** до сохранения → «Редактирование → Сохранить
  изменения». (Подтверждает семантику red=dirty, обсуждавшуюся ранее.)
- **Служебные поля** «Оператор» и «Дата изменения» заполняются автоматически, пользователь их
  НЕ редактирует. (Поэтому в inline-гриде их колонки правомерно пропускаются.)
- `*` = обязательное поле. **НДЗ/КДЗ** = начало/конец действия записи.
- Сообщения об ошибках — префикс «Ошибка:» (наш detect ОШИБКА/Ошибка корректен).

## Реальные UI-флоу по сущностям АИС ГСК (ground truth)
| Сущность | Меню/путь | Тип флоу | Add | Edit | Delete |
|---|---|---|---|---|---|
| **ГСК/ОГСК** | ГСК → ГСК/ОГСК → Добавить | **Модалка (карточка)** | карточка → «Готово» | Найти → «Сведения ГСК/ОГСК» → правка(красным) → Сохранить изменения | Редактирование→Удалить |
| **Совещание** | ГСК → Совещание → Добавить | **Модалка** | карточка → Готово | «Сведения совещания» → Сохранить изменения | — |
| **Должностные лица** (НСИ) | НСИ → Должностные лица → Открыть/Найти | **Inline-грид (Type 2)** | Редактирование→Добавить → ПУСТАЯ СТРОКА → заполнить → Сохранить изменения | выбрать строку → правка → Сохранить изменения | Редактирование→Удалить |
| **Причина смены предс./предст.** (НСИ) | НСИ → … | **Inline-грид (Type 2)** — «по аналогии с Должностными лицами» | как выше | как выше | как выше |
| **Документ ГСК/ОГСК** | ЛКМ ГСК в дереве → вкладка «Документы ГСК/ОГСК» → нижнее окно | **Inline-грид во вкладке (CHILD)** | Редактирование→Добавить → СТРОКА → заполнить (файл через «+») → Сохранить изменения | выбрать → правка → Сохранить изменения | Редактирование→Удалить |
| **Документ совещания** | вкладка в Совещании | как Документ ГСК (inline) | inline-строка | inline | Удалить |
| **Приглашённый ГСК** | ЛКМ Совещание → вкладка «Приглашённые ГСК» → нижнее окно | **Inline-грид во вкладке (CHILD)** | Редактирование→Добавить → СТРОКА → Сохранить изменения | inline | Удалить |
| **Участник совещания** | вкладка в Совещании | **Inline-грид во вкладке (CHILD)** | inline-строка | inline | Удалить |
| **Повестка совещания** | **ПКМ Совещание в дереве → Повестка → Добавить** | **Модалка через узел дерева** | карточка → Готово | «Сведения повестки» → Сохранить изменения | Удалить |
| Отчёты | Совещание → Найти → «Отчёты» → Сформировать | — | — | — | — |

Ограничения: запись с заполненным **КДЗ** нельзя удалить/изменить; запись, **используемую в
объектах**, нельзя удалить. **Лог. изменить** = сохранение с историей (сначала новый НДЗ).

## Где наш генератор РАСХОДИТСЯ с документацией (роадмап точности)
1. **CHILD grid-вкладки (Документы/Приглашённые/Участники) редактируются INLINE в гриде**, а не
   модальной формой. Наш `writeChildCreateTest` жмёт тулбар «Добавить» и ждёт `waitForAddForm()`
   (модалку) → её нет → skip/fail. **Надо**: для child-grid использовать inline-механику Type 2
   (Редактирование→Добавить → заполнить ячейки с клавы/по маске → Сохранить изменения), как в
   `writeInlineTableCreateTest`. Это и есть причина оставшихся skip у дочерних.
2. **«Должностные лица» (НСИ) — inline-справочник (Type 2)**, а singular «Должностное лицо» —
   карточка-пикер. Сейчас генерим модальный CRUD на «Должностное лицо» и почти ничего на
   «Должностные лица». **Надо**: править классификацию (twin/`nameStemsMatch` ломается на
   «должностны*е*»/«должностно*е*») — inline-CRUD вешать на «Должностные лица».
3. **Повестка совещания — модальный CRUD через узел дерева** (ПКМ → Повестка → Добавить →
   карточка → Готово). Сейчас для tree-node генерим только presence-тест полей. **Надо**: для
   tree-node можно добавить реальный create/update/delete через карточку из узла.
4. **«Обновить» в пагинации грида = наш `clickGridRefresh`**, «общее число записей» = наш
   счётчик — концепция верна, подтверждено.
5. **red=изменено (dirty) до «Сохранить изменения»** — подтверждает прежние правки (ввод с
   клавы → строка красная → Сохранить).
6. **Логическое изменение** требует сначала проставить новый НДЗ — наш `testLogicalEdit` этого
   не делает (мелочь).
7. Параметр поиска «Отображение результата» (поисковая система vs модуль) — учитывать для
   generic-навигации/чтения результатов.

## Вывод для «шаблонности» (новые XML)
Классификацию и выбор флоу надо вести по СТРУКТУРЕ метаописания (тип группы свойств: Карточка
vs Грид; наличие `<Operation><Modifier>`; ассоциации addFromTree/flag_display; параметры
поиска), а НЕ по именам. Грид-группа (своя или во вкладке родителя) ⇒ inline-CRUD;
карточка с операциями ⇒ модальный CRUD; узел дерева с карточкой ⇒ модальный CRUD из дерева;
read-only (нет модификаторов) ⇒ только presence/grid-проверка.
