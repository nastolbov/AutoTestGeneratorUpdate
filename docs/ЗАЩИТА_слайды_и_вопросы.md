### Слайд 1 — Титул (15 сек)
**На слайде:** тема, ФИО, руководитель, год.
**Сказать:** «Тема моей работы — разработка информационной системы, которая
автоматически генерирует автотесты для веб-приложения по его XML-модели данных.»

### Слайд 2 — Проблема и актуальность (40 сек)
**На слайде:** 3 пункта:
- Ручное тестирование CRUD-форм в корпоративной системе E3Core — долго и однообразно.
- Структура форм уже описана в XML-метамодели (сущности, поля, операции, поиски).
- Значит, тесты можно не писать руками, а порождать из этой модели.

**Сказать:** «В системе на платформе E3Core десятки справочников и форм. Тестировать
их вручную дорого. Но вся структура форм уже формализована в XML. Идея работы — взять
эту модель как источник истины и автоматически построить по ней рабочие автотесты.»

### Слайд 3 — Цель и задачи (40 сек)
**На слайде:**
- **Цель:** ИС, генерирующая исполняемые автотесты web-интерфейса из XML-модели.
- **Задачи:** разобрать XML → классифицировать сущности → сгенерировать Selenium/JUnit-проект
  → запустить и собрать результаты → сохранить историю и отчёты.

**Сказать:** «Цель — система полного цикла: от XML до зелёного/красного результата с отчётом.»

### Слайд 4 — Что на входе: XML-метамодель (40 сек)
**На слайде:** фрагмент XML + что из него берём:
- сущности (EntityObject), группы свойств (Карточка / Грид), поля и типы, маски;
- операции CRUD (Operation/Modifier), поиски (Search) и их параметры.

**Сказать:** «На входе — выгрузка метамодели. Парсер на StAX потоково читает её и строит
доменную модель: сущности, их поля с типами и масками, доступные операции и поисковые формы.
Три XML-неймспейса (NS_E/NS_E3/NS_MD) вынесены в константы.»

### Слайд 5 — Архитектура: слои и пакеты (50 сек)
**На слайде:** диаграмма пакетов со стрелками (однонаправленные):
`ui → {parser, generator, data, model, common}`, `parser → model`,
`generator → {model, data, common}`, всё → `common`.
6 пакетов: **ui** (JavaFX), **parser** (StAX), **model** (домен + классификатор),
**generator** (ядро генерации + запуск + отчёт), **data** (SQLite), **common** (утилиты).

**Сказать:** «Архитектура слоистая, зависимости однонаправленные, циклов нет. UI знает про
доменную модель и генератор, а домен про UI — ничего. Это упрощает сопровождение и тестирование.»

### Слайд 6 — Ключевой алгоритм №1: классификация сущностей (50 сек)
**На слайде:** блок-схема `EntityClassifier`:
grid-вкладка → tree-node → префикс V_S_ → pick-one-поиск → FK-target-only → иначе **PRIMARY**.
3 категории: **PRIMARY** (свой тест-класс) / **CHILD** (тест внутри карточки родителя) /
**REFERENCE_DICTIONARY** (справочник-пикер — пропускаем).

**Сказать:** «Первый ключевой алгоритм — классификатор. Он по СТРУКТУРЕ метамодели, а не по
именам, решает, что и как тестировать: самостоятельная сущность получает отдельный тест-класс,
дочерняя — тест в составе родителя, а справочники-пикеры пропускаются. За счёт структурного
подхода система переносится на любую E3Core-модель без правки кода.»

### Слайд 7 — Ключевой алгоритм №2: выбор CRUD-сценария и навигация (50 сек)
**На слайде:** две ветки:
- **Тип 1 (модальная карточка):** меню → Добавить → форма → заполнение → Готово.
- **Тип 2 (inline-грид):** Редактирование → Добавить → строка → заполнение по маске → Сохранить.
+ навигация E3Core: дерево поисков → «по параметрам» → Выполнить (с приоритетом нужной кнопки меню).

**Сказать:** «Второй алгоритм — выбор сценария CRUD по типу группы свойств: для карточек —
модальный поток, для гридов — построчное редактирование. Навигация по дереву поисков и
заполнение полей идут по маскам из модели (например, даты `dd.MM.yyyy`), служебные поля
вроде «Оператор» пропускаются.»

### Слайд 8 — Достоверность тестов (важно методологически) (45 сек)
**На слайде:**
- Проверка по **уникальному маркеру** + **счётчику «Всего записей»**.
- **Seed-then-delete**: тест сам создаёт запись и удаляет именно её.
- **Честный FAIL** при серверной ошибке — никаких «зелёных заглушек».

**Сказать:** «Отдельное внимание — честности тестов. Тест подтверждает результат по уникальному
маркеру и счётчику записей, удаляет именно ту запись, что создал, и при реальной ошибке сервера
честно краснеет. Это отличает систему от генераторов, дающих ложно-зелёный результат.»

### Слайд 9 — Хранение данных: БД и отчёты (40 сек)
**На слайде:** ER-схема двух таблиц:
- `test_run` (id, run_date, xml_file, base_url, total, passed, failed, skipped, duration_ms)
- `test_case` (id, run_id→test_run, class_name, method_name, passed, failure_msg, duration_ms), связь 1:N.
+ отчёты: `run-report.html` (с фотолетописью-скриншотами), surefire-html, CSV.

**Сказать:** «Каждый прогон сохраняется в встраиваемую SQLite: шапка прогона и его тест-кейсы,
связь один-ко-многим. Запись идёт одной транзакцией. Дополнительно строятся наглядные
HTML-отчёты со скриншотами шагов.»

### Слайд 10 — Результаты и вывод (40 сек)
**На слайде:** скриншот главного окна (макет) + цифры последнего прогона (Всего/OK/Ошибки).
Вывод: система проходит полный цикл, тесты исполняются на реальном стенде, результат достоверный.

**Сказать:** «В результате получена работающая ИС: разбирает XML, строит и запускает тесты на
реальном стенде, сохраняет историю и отчёты. Достоверность подтверждена прогонами. Спасибо за

## ЧАСТЬ 2. ВОПРОСЫ И ОТВЕТЫ

### A. Алгоритмы

**Q: Как система понимает, по каким сущностям генерировать тесты?**
Класс `EntityClassifier.classify(entity, model)` возвращает категорию: PRIMARY (отдельный
тест-класс), CHILD (тест внутри родителя) или REFERENCE_DICTIONARY (пропуск). Решение — по
структуре метамодели: есть ли grid-вкладка, узел дерева (addFromTree), префикс `V_S_`,
pick-one-поиск, является ли сущность только FK-целью. Имена не используются — поэтому подход
переносим на любую модель.

**Q: Чем отличаются «два типа» CRUD?**
Тип 1 — модальная карточка (PropertyGrid): открывается отдельное окно, поля заполняются,
финальная кнопка «Готово». Тип 2 — inline-грид (editorgrid): строка добавляется и редактируется
прямо в таблице, затем «Сохранить изменения». Выбор делается по типу группы свойств в модели.

**Q: Как заполняются поля разных типов?**
`TestDataFactory` генерирует значение по типу и маске поля. Для дат — реальная дата по маске
(`99.99.9999` → `dd.MM.yyyy`), для строк — уникальный маркер. Маски, превращающие ввод в
«12ч34мин», обрабатываются вводом только цифр. Служебные поля («Оператор», «Дата изменения»)
пропускаются, обязательные (по «*») — учитываются.

**Q: Как устроена навигация по интерфейсу?**
Это E3Core/ExtJS: верхнее меню → «Дерево поисков» → узел «по параметрам» → форма → «Выполнить».
Нужная кнопка меню ищется динамически и ставится в приоритет (кэшируется для последующих
навигаций), узлы дерева активируются через ExtJS-API с фолбэком на клики — это устойчивее, чем
голые координаты.

**Q: Как тест убеждается, что запись реально создана/удалена?**
По уникальному маркеру (фильтрованный поиск / DOM / ExtJS-store) И по счётчику «Всего записей».
Для удаления используется seed-then-delete: тест создаёт свою запись, находит её по маркеру,
удаляет и проверяет, что она исчезла, а счётчик уменьшился.

### B. Код и архитектура

**Q: Из каких пакетов состоит система?**
6 пакетов: `ui` (JavaFX-интерфейс), `parser` (StAX-разбор XML), `model` (доменные классы +
`EntityClassifier`), `generator` (`TestGenerator`, `TestClassWriter`, `PageObjectWriter`,
`TestRunner`, `RunReportWriter`, `TestDataFactory`, `TestConfig`), `data` (SQLite DAO),
`common` (`Transliterator`, `JavaFileWriter`, `ParserException`). Зависимости однонаправленные.

**Q: Есть ли связь между `ui` и `model`?**
Да, односторонняя: `MainController` импортирует `AppModel`, `EntityObject`, `EntityClassifier`,
`EntityKind`, `TestRunResult`, `TestCaseResult`. Обратной зависимости `model → ui` нет.

**Q: Как генерируется сам Java-код тестов?**
Генераторы пишут исходники построчно через `JavaFileWriter` (`w.writeLine(...)`). Порождается
полноценный Maven-проект: `pom.xml`, `BaseTest`, `SharedDriver`, по каждому объекту `<Имя>Page`
(Page Object) и `<Имя>Test` (JUnit5 + Selenium). То есть система — это двухуровневая модульность:
сама ИС и генерируемый ею модульный артефакт.

**Q: Почему Page Object?**
Чтобы отделить локаторы/действия со страницей от логики теста — стандартный паттерн Selenium,
повышает читаемость и снижает дублирование.

**Q: Как имена сущностей превращаются в имена классов?**
`Transliterator.toClassName / toMethodName / toFieldName` — транслитерация кириллицы в
корректные Java-идентификаторы.

**Q: Какой стек технологий?**
Java 17, JavaFX 24 (GUI), StAX (парсинг), Selenium + JUnit 5 (в генерируемых тестах),
Maven (сборка и запуск), SQLite через драйвер xerial `sqlite-jdbc` 3.42.

### C. Функционал

**Q: Опишите сценарий работы пользователя.**
Выбрать XML → «Разобрать XML» (слева появляется дерево: что будет тестироваться, что нет) →
указать URL/логин/пароль и каталог → «Сгенерировать тесты» → «Запустить тесты». Результаты —
в таблице (Класс/Метод/Статус/Время/Сообщение) и в логе; отчёты — в `target/`.

**Q: Что показывает дерево слева?**
Две группы: «✓ Будут протестированы» (PRIMARY с вложенными CHILD) и «✗ Тесты не генерируются»
(справочники/FK). Цвета: зелёный — отдельный тест, янтарный — в составе родителя, серый — без
тестов. Дерево строится тем же `EntityClassifier`, что и генерация, — они не расходятся.

**Q: Что за «Скрыть визуальную работу браузера»?**
Это headless-режим Chrome: тесты идут без видимого окна браузера — быстрее и удобно для
фонового прогона. Для визуального контроля галочку снимают.

**Q: Как запускаются тесты?**
`TestRunner` вызывает внешний `mvn test` в сгенерированном проекте (на Windows — `mvn.cmd`),
Surefire-результаты разбираются и попадают в таблицу/БД. Мутирующие тесты идут последовательно
(forkCount=1), т.к. параллельные сессии одного логина конфликтуют по данным.

**Q: Что в отчётах?**
`run-report.html` — наглядный отчёт с «фотолетописью» (скриншоты шагов), стандартный
surefire-html, CSV и папка скриншотов. История прошлых прогонов берётся из SQLite.

### D. База данных (упор)

**Q: Какая СУБД и почему?**
Встраиваемая SQLite через драйвер xerial `sqlite-jdbc` 3.42. Выбор обоснован: не требует
установки сервера, файл БД создаётся автоматически, достаточно для локальной истории прогонов.

**Q: Где лежит БД и когда создаётся?**
Файл `autotestgen.db` в рабочем каталоге (`DatabaseConnection.DEFAULT_URL =
"jdbc:sqlite:autotestgen.db"`). Схема создаётся при старте `SchemaInitializer.initialize()`
через `CREATE TABLE IF NOT EXISTS` — то есть автоматически при первом запуске.

**Q: Опишите схему.**
Две таблицы, связь 1:N:
- `test_run` — шапка прогона: `id` PK AUTOINCREMENT, `run_date`, `xml_file`, `base_url`,
  `total`, `passed`, `failed`, `skipped`, `duration_ms`.
- `test_case` — отдельный тест: `id` PK, `run_id` → `test_run(id)`, `class_name`,
  `method_name`, `passed` (0/1), `failure_msg` (nullable), `duration_ms`.

**Q: Как организован доступ к данным (паттерн)?**
Паттерн DAO + фасад. `ReportDao` — фасад с методами `saveRun`/`getAllRuns`, внутри делегирует
`TestRunDao` и `TestCaseDao`; подключение инкапсулировано в `DatabaseConnection`, DDL — в
`SchemaInitializer`. Это разделение ответственности: соединение, схема, и две таблицы — каждое
в своём классе.

**Q: Как обеспечивается целостность при сохранении?**
`ReportDao.saveRun` отключает автокоммит (`setAutoCommit(false)`), вставляет шапку
(`testRunDao.insert`), затем пакетно тест-кейсы (`testCaseDao.insertBatch`) и делает один
`commit()`. При ошибке транзакция не фиксируется — прогон не сохранится частично.

**Q: Контролируется ли внешний ключ на уровне СУБД?**
FK `test_case.run_id → test_run(id)` объявлен декларативно в DDL, но в коде нет
`PRAGMA foreign_keys=ON`, поэтому SQLite его принудительно не проверяет — целостность
обеспечивается логикой DAO (run_id берётся от только что вставленной шапки). Это честная
формулировка для защиты.

**Q: Почему «INTEGER/TEXT», а не «Number/String»?**
В SQLite типы — это affinity: целые/флаги хранятся как `INTEGER`, строки как `TEXT`. Поле
`passed` — INTEGER 0/1 (булев флаг), `failure_msg` — nullable TEXT.

**Q: Используете ли защиту от SQL-инъекций?**
Да — все вставки идут через `PreparedStatement` с параметрами, конкатенации значений в SQL нет.

**Q: Как закрываются ресурсы?**
Через try-with-resources (`Connection`/`Statement`/`ResultSet` закрываются автоматически),
что исключает утечки соединений.

## ЧАСТЬ 3. «КАВЕРЗНЫЕ» ВОПРОСЫ — короткие ответы

- **Почему не существующий фреймворк (например, генератор по Swagger)?** Здесь источник — не
  REST-контракт, а XML-метамодель GUI-форм E3Core; готовых генераторов под неё нет, тесты —
  именно UI-уровня (Selenium).
- **Чем подход универсален?** Классификация и выбор сценария идут по структуре модели, а не по
  именам сущностей — на новой E3Core-модели код менять не нужно.
- **Главная сложность?** Достоверность на реальном стенде: устойчивая навигация ExtJS и
  проверка результата по маркеру+счётчику, чтобы не было ложно-зелёных.
- **Что бы развивали дальше?** Параллельный прогон (инфраструктура уже заложена: forkCount,
  уникальный user-data-dir на форк), расширение типов полей, поддержка других платформ.
- **Тестировали ли саму систему?** Да, многократными прогонами на реальном стенде с разными
  XML; сверка дерева классификации с журналом генерации и отчётами.
