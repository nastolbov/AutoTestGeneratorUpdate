# Как работает AutoTestGenerator — объяснение «на пальцах»

> Этот документ написан так, чтобы понял человек, далёкий от программирования.
> Сначала — простые аналогии. Потом — где это лежит в коде. В конце — как
> поддерживать программу (что и где менять, как собирать, как читать ошибки).

---

## 1. Что вообще делает программа (одна большая аналогия)

Представьте, что у вас есть **большое веб-приложение** (сайт с формами: завести
организацию, изменить, удалить, найти). Чтобы убедиться, что оно работает, нужен
**тестировщик**: человек, который руками открывает каждую форму, заполняет поля,
жмёт «Сохранить», ищет запись, проверяет, что всё сохранилось. Это долго и скучно.

**AutoTestGenerator — это «робот-тестировщик», который сам пишет себе инструкцию и
сам её выполняет.** Но робот не умеет догадываться, какие в приложении формы и поля.
Поэтому ему дают **«чертёж» приложения — XML-файл**. В этом чертеже описано:
какие есть экраны (сущности), какие на них поля, какие кнопки (Добавить/Изменить/
Удалить), какие есть поиски.

Программа делает 5 вещей по очереди:

1. **Читает чертёж** (XML) и понимает структуру приложения.
2. **Сортирует** экраны на 3 вида (главные, вложенные, справочники).
3. **Пишет тесты** — то есть генерирует готовые программы-роботы (на языке Java).
4. **Запускает** эти программы: открывается браузер, робот кликает и печатает.
5. **Делает отчёт**: что прошло (✓), что упало (✗), со скриншотами.

Аналогия целиком:
> Вы даёте роботу чертёж дома (XML). Робот читает чертёж, понимает, где двери и окна
> (поля и кнопки), сам пишет себе памятку «зайти, открыть окно, проверить» (тесты),
> потом обходит дом (запускает браузер) и составляет акт осмотра (отчёт).

## 2. Шаг 1 — Чтение чертежа (парсинг XML)

### Простыми словами
XML — это текстовый файл, где всё описано «ёлочкой» из тегов. Программа читает его
**сверху вниз, по одному тегу**, как человек читает книгу слово за словом, и
складывает прочитанное в свою «память» (объекты в оперативной памяти).

Что она вытаскивает из чертежа:
- **Сущность (Object)** — это один экран/карточка, например «ГСК/ОГСК» или «Совещание».
  У неё есть имя, ключ (как её отличать от других) и техническое имя таблицы.
- **Группа свойств (Properties)** — это вкладка на экране. Бывает двух видов:
  **форма** (поля для одной записи) и **грид** (таблица из многих записей).
- **Свойство (Property)** — одно поле ввода: имя («Адрес ГСК»), тип (текст / число /
  дата), обязательное ли оно (звёздочка `*`), и **маска** (шаблон ввода, например
  `99.99.9999` для даты).
- **Операция (Operation)** — что можно делать с записью: Добавить (I), Сохранить
  изменения (U), Удалить (D), и т.п. Это будущие кнопки, которые робот будет нажимать.
- **Поиск (Search)** — форма-фильтр: какие параметры ввести, чтобы найти записи, и
  какие колонки покажет таблица результатов.
- **Связь (Association)** — кто с кем связан. Например, поле «Район» в форме ГСК берёт
  значения из справочника «Район». Или вкладка «История» живёт внутри карточки ГСК.

### Где это в коде
- `parser/XmlModelParser.java` — главный «чтец». Метод `parse(File)` идёт по тегам и
  раздаёт работу помощникам.
- `parser/EntityParser.java` — вытаскивает сущности и их связи.
- `parser/PropertyGroupParser.java` — вытаскивает вкладки, поля и операции.
- `parser/SearchParser.java` — вытаскивает поиски.
- Результат складывается в `model/AppModel.java` — это «папка», где лежит вся
  прочитанная структура: список сущностей и список поисков.

> Технически чтение идёт через **StAX** — это способ читать XML по событиям
> («начался тег», «закончился тег»), не загружая весь файл в память целиком.
> Думайте об этом как о конвейере: тег проехал — обработали — забыли.

## 3. Шаг 2 — Сортировка сущностей на 3 вида

### Зачем
Не для каждого экрана нужны отдельные тесты. Например, справочник «Район» сам по себе
не тестируется — он нужен только как выпадающий список в других формах. Поэтому
программа **классифицирует** каждую сущность.

### Три вида (простыми словами)
1. **PRIMARY (главная)** — самостоятельный экран с меню, поиском и кнопками
   Добавить/Изменить/Удалить. ➜ Для неё пишется **отдельный тест**.
   *Цвет в дереве программы — зелёный.*
2. **CHILD (вложенная)** — вкладка-таблица внутри другой карточки (например «История»
   внутри «ГСК») или узел в дереве. ➜ Тест есть, но он сначала открывает родителя.
   *Цвет — жёлтый.*
3. **REFERENCE_DICTIONARY (справочник)** — нужен только как выпадающий список.
   ➜ **Тесты не пишутся.** *Цвет — серый.*

### Как программа решает (алгоритм)
По порядку проверяет:
1. Имя сущности совпадает с именем какой-то таблицы-вкладки внутри другой сущности,
   и у неё нет своих кнопок? → **вложенная (грид)**.
2. На неё указывает связь «добавляется из дерева»? → **вложенная (узел дерева)**.
3. Её техническое имя начинается на `V_S_` (платформенная пометка «системный
   справочник») ИЛИ все её поиски «без параметров» (просто выбрать одно значение)? →
   **справочник**.
4. Иначе → **главная**.

### Где это в коде
- `model/EntityClassifier.java`, метод `classify(...)` — вся логика сортировки.
- `model/EntityKind.java` — перечисление трёх видов (PRIMARY / CHILD / REFERENCE_DICTIONARY).

> Это **самый «умный» алгоритм** в программе. Если робот вдруг пишет тест там, где не
> надо (или пропускает нужный экран) — причина почти всегда здесь.

## 4. Шаг 3 — Написание тестов (генерация кода)

### Простыми словами
Теперь программа из «памяти» (AppModel) **пишет настоящие файлы программ-роботов** —
готовый проект на Java. Это как если бы вы по чертежу дома напечатали подробную
пошаговую памятку для каждого осмотрщика.

Что создаётся:
- **`pom.xml`** — список «инструментов», которые нужны роботу (браузер Selenium,
  фреймворк тестов JUnit, менеджер драйвера браузера). Это как список инвентаря.
- **Вспомогательные классы** (`BaseTest`, `SharedDriver`, `TestData`) — общие функции:
  открыть браузер, залогиниться, общие данные.
- **Для каждой ГЛАВНОЙ сущности — два файла:**
  - **Page Object** (например `GskOgskPage.java`) — «карта экрана»: методы вроде
    «заполни поле Адрес», «найди первую запись», «нажми Удалить». Это паттерн:
    отдельно описываем, *как* кликать по конкретному экрану.
  - **Тест-класс** (например `GskOgskTest.java`) — собственно проверки: создать,
    изменить, удалить, найти, проверить обязательные поля.

### Из чего робот берёт, что вводить в поля (тестовые данные)
Робот не может вписать в поле «дата» слово «привет» — сервер не примет. Поэтому есть
**фабрика тестовых данных**:
- текстовое поле → `Test_имяполя`;
- число → случайное (например 100–999);
- дата → сегодняшняя в нужном формате;
- если у поля есть **маска** (`99.99.9999`, `99-99`) → значение генерируется строго
  по шаблону: где `9` — подставит цифру, где буква — букву, разделители (`.`, `-`)
  оставит как есть.

### Типы проверок, которые попадают в тест
| Проверка | Что делает робот |
|----------|------------------|
| `testFieldsPresent` | смотрит, что все поля на экране есть |
| `testCreate` | создаёт новую запись и находит её в таблице |
| `testUpdate` | меняет запись и проверяет изменение |
| `testDelete` | удаляет запись |
| `testRequiredFieldValidation` | проверяет, что без обязательных полей не сохранить |
| `testSearch*` | проверяет каждый поиск |
| `testGrid*` | проверяет каждую таблицу (колонки/кнопки) |

### Где это в коде
- `generator/TestGenerator.java` — «дирижёр»: создаёт папки, проходит по всем
  сущностям, для главных вызывает написание Page Object и теста.
- `generator/PageObjectWriter.java` — пишет «карту экрана» (как кликать).
- `generator/TestClassWriter.java` — пишет сами проверки.
- `generator/TestDataFactory.java` — придумывает значения для полей (и по маске).
- `generator/TestConfig.java` — настройки генерации (URL, логин, пароль, папка, тип сайта).
- `common/Transliterator.java` — превращает русские имена в латиницу для имён файлов
  («ГСК/ОГСК» → `GskOgsk`).
- `common/JavaFileWriter.java` — аккуратно печатает строки Java-кода с отступами.

> Важно понять: программа **не запускает** тесты в этот момент. Она их только
> **печатает в файлы**. Это как написать сценарий — играть по нему будут позже.

## 5. Шаг 4 — Запуск тестов

### Простыми словами
Теперь напечатанный проект нужно «проиграть». Программа запускает **Maven** (это
инструмент сборки и запуска Java-проектов) командой `mvn test`. Maven компилирует
роботов и запускает их: **открывается браузер Chrome**, робот заходит на сайт,
логинится, выбирает подсистему, открывает формы, печатает, кликает, проверяет.

Особенности:
- Тесты идут **по очереди, один браузер за раз** (`forkCount=1`). Почему: если
  запустить несколько браузеров на одном логине, они «дерутся» за одну и ту же запись
  и мешают друг другу.
- Есть «быстрый режим» (fastMode / headless) — браузер работает **невидимо**, без окна,
  чуть быстрее.
- Программа **на ходу читает то, что печатает Maven**, и показывает это в логе в
  своём окне — вы видите прогресс в реальном времени.

### Где это в коде
- `generator/TestRunner.java` — находит Maven, строит команду, запускает процесс,
  читает его вывод строка за строкой, потом читает отчёты о результатах.

## 6. Шаг 5 — Отчёт и сохранение результатов

### Простыми словами
После прогона Maven оставляет «протоколы» (XML-файлы в папке `surefire-reports`).
Программа их читает и превращает в понятный результат:
- сколько тестов всего, сколько ✓ прошло, ✗ упало, ⏭ пропущено;
- по каждому упавшему тесту — **текст ошибки**, **скриншоты по шагам**, какие данные
  вводились, сколько времени занял каждый шаг.

Результаты:
- показываются **в таблице в окне программы**;
- сохраняются в **базу данных** `autotestgen.db` (чтобы видеть историю прогонов);
- выгружаются в **HTML-отчёт** `run-report.html`, который можно открыть в браузере и
  показать кому угодно.

### Где это в коде
- `generator/RunReportWriter.java` — делает красивый HTML-отчёт.
- `data/` — работа с базой: `SchemaInitializer` (создаёт таблицы), `TestRunDao`,
  `TestCaseDao`, `ReportDao` (сохраняют и читают историю).
- `data/DatabaseConnection.java` — соединение с базой SQLite.

## 7. Что вы видите в окне программы (интерфейс)

- **Поля сверху**: путь к XML, URL приложения, логин/пароль, папка для тестов.
- **Кнопки**: «Разобрать XML» (прочитать чертёж), «Сгенерировать» (написать тесты),
  «Запустить», «История прогонов».
- **Слева — дерево сущностей**: зелёные = будут тесты, жёлтые = вложенные тесты,
  серые = справочники (без тестов).
- **Справа сверху — таблица результатов**, снизу — **лог** (что происходит сейчас).

### Где это в коде
- `ui/App.java` — запуск окна.
- `ui/MainController.java` — что происходит при нажатии кнопок.
- `ui/Launcher.java` — точка входа программы.
- `resources/fxml/main.fxml` — расположение элементов окна (внешний вид).

## 8. Полный маршрут «от чертежа до отчёта» (одной картинкой словами)

```
XML-чертёж
   │  (Шаг 1: парсеры читают теги)
   ▼
AppModel  ── список сущностей и поисков в памяти
   │  (Шаг 2: EntityClassifier сортирует на 3 вида)
   ▼
зелёные / жёлтые / серые сущности
   │  (Шаг 3: TestGenerator + Writer'ы печатают .java-файлы)
   ▼
готовый Maven-проект (Page Object'ы + Тесты + pom.xml)
   │  (Шаг 4: TestRunner запускает `mvn test`, открывается браузер)
   ▼
протоколы прогона (surefire-reports)
   │  (Шаг 5: читаем результаты)
   ▼
таблица в окне  +  база autotestgen.db  +  run-report.html
```

## 9. Как поддерживать программу (главное для вас)

### 9.1 Куда смотреть, если что-то не так
| Симптом | Где искать причину |
|---------|--------------------|
| XML читается неправильно, теряются поля/сущности | `parser/` (XmlModelParser, EntityParser, PropertyGroupParser, SearchParser) |
| Экран попал не в тот «цвет» (есть лишний тест или пропал нужный) | `model/EntityClassifier.java` |
| В сгенерированном тесте кривой клик/локатор/поле | `generator/PageObjectWriter.java` |
| Не хватает проверки (нужен новый вид теста) | `generator/TestClassWriter.java` |
| В поле подставляется неправильное значение | `generator/TestDataFactory.java` |
| Тесты не запускаются / не находится Maven | `generator/TestRunner.java` |
| Кривой/неполный HTML-отчёт | `generator/RunReportWriter.java` |
| Кнопка в окне делает не то | `ui/MainController.java` |
| Имя сгенерированного файла странное | `common/Transliterator.java` |

### 9.2 Типичные задачи сопровождения
- **Сменить стенд (URL/логин/пароль)**: пока что заданы по умолчанию в
  `ui/MainController.java` (метод инициализации, где `urlField.setText(...)` и т.д.).
  Меняются и прямо в окне перед генерацией.
- **Добавить новый тип проверки** (например, «проверить сортировку грида»):
  добавить метод-генератор в `TestClassWriter.java` и вызвать его там, где
  перечисляются остальные `testXxx`.
- **Поправить, как заполняется конкретный тип поля**: смотреть
  `PageObjectWriter.fillPropertyGridField(...)` и `TestDataFactory.generateValue(...)`.
- **Поддержать новую конвенцию справочников**: правка условий в
  `EntityClassifier.isReferenceDictionary(...)`.

### 9.3 Как собрать и запустить
- Сборка проекта: `mvn -q package` (использует `pom.xml` в корне).
- Запуск окна: `2_ЗАПУСК.bat` (Windows) или через Maven-плагин JavaFX.
- Установка окружения в первый раз: `1_УСТАНОВКА.bat`.
- Внутри сгенерированного проекта тесты запускаются `mvn test` (это делает за вас
  кнопка «Запустить»).

### 9.4 Как читать ошибку упавшего теста
1. В таблице результатов найдите строку с ✗ — там класс и метод (например
   `GskOgskTest.testCreate`).
2. Откройте `run-report.html` — у этого теста будет текст ошибки и **скриншоты по
   шагам**: видно, на каком именно действии робот «споткнулся».
3. Если ошибка в локаторе (робот не нашёл поле/кнопку) — правка в Page Object.
   Если сервер вернул ошибку (например про дату) — это поведение тестируемого
   приложения, а не баг генератора.

### 9.5 Золотое правило
> Программа **ничего не знает про конкретное приложение сама** — всё берётся из XML.
> Поэтому 90% «странного поведения» — это либо особенность XML-чертежа, либо логика
> сортировки в `EntityClassifier`. Начинайте разбор именно с них.

## 10. Мини-словарь терминов

- **Сущность / Object** — один экран-карточка приложения.
- **Грид** — таблица из многих записей.
- **Форма** — экран для одной записи (с полями).
- **CRUD** — Create/Read/Update/Delete (создать/прочитать/изменить/удалить).
- **Маска** — шаблон ввода поля (`99.99.9999` — дата).
- **Page Object** — класс-«карта экрана»: как кликать по конкретной форме.
- **Selenium** — инструмент, который управляет браузером как человек.
- **JUnit** — фреймворк, который запускает проверки и говорит ✓/✗.
- **Maven** — инструмент, который собирает и запускает Java-проект.
- **StAX** — способ читать XML по событиям (по одному тегу).
- **SQLite (`autotestgen.db`)** — маленькая база данных в одном файле (история прогонов).
```
