# AutoTestGenerator — обновление v3 (auto-discovery + глубокая навигация)

Документ описывает, что изменилось по сравнению с исходной версией в ветке `main`.
Все доработки направлены на повышение покрытия XML-моделей и надёжность авто-тестов,
работающих с веб-интерфейсом E3Core (ExtJS).

## Кратко

- Добавлен **smoke-режим автоматического обхода всех подсистем** XML-модели —
  одной кнопкой запускается генерация и прогон тестов для каждой подсистемы.
- Полностью переписана **навигация по меню E3Core**: теперь поддерживаются
  каскадные подменю ExtJS, склонения русских названий, fallback-кнопка
  «Открыть» и несколько стратегий клика.
- Поиск «по параметрам» теперь действительно открывает форму поиска,
  заполняет её, нажимает «Выполнить поиск» и **проверяет видимость полей
  в гриде результатов** — раньше это был фиктивный smoke.
- Прогон стабилизирован: `forkCount=1`, перезапуск браузера между
  подсистемами, кэширование результата навигации.
- В отчёт выведены **реальные причины пропусков** и сделаны скриншоты
  на каждом сбое — диагностика стала прозрачной.

## Изменения по слоям

### 1. Auto-discovery подсистем (CLI и UI)

- `CliRunner` принимает новые флаги:
  - `--smoke-all-subsystems true|false` (по умолчанию `true`)
  - `--no-smoke` — отключить smoke
- Если `--subsystem` не задан, имя подсистемы автоматически берётся
  из `CategoryName` XML-модели (метод `AppModel.getSubsystemNameFromCategory`).
- В FXML и `MainController` добавлен чекбокс «Smoke-тест всех подсистем»
  для GUI-режима.

### 2. Навигация по меню ExtJS (`TestGenerator.navigateE3Core`)

- Перебираются основные кнопки верхней панели:
  `<подсистема>` → `НСИ` → `Отчёты` → `Сервис`.
- Реализован **рекурсивный `descendMenu`** с ограничением глубины,
  множеством уже посещённых пунктов и корректным повторным поиском
  всплывающего подменю после его перерисовки.
- Между подсистемами браузер перезапускается, чтобы не тащить
  залипшие состояния ExtJS.

### 3. Сопоставление названий по корням слов

- Метод `entityStemPredicate` строит XPath-предикат по корням слов
  (отбрасывает последние 2 символа каждого слова длиннее 3 символов).
- Это позволяет находить пункт меню «Должностные лица» по сущности
  XML «Должностное лицо», «Совещания» по «Совещание» и т.п.
- Помимо «Найти» поддерживается **fallback на «Открыть»** —
  справочники без поиска теперь тоже навигируются.

### 4. Каскадные стратегии клика

Для пунктов меню и кнопок применяются последовательно:
- `WebElement.click()`
- `Actions.click()`
- эмуляция `mousedown`+`mouseup` через JS
- `JavascriptExecutor.click()`

Это обходит характерные баги ExtJS, когда обработчик висит не на `click`,
а на `mousedown`/`mouseup` или на дочернем элементе.

### 5. Поиск «по параметрам»

- В дереве выбора поиска по узлу «по параметрам» делается **double-click** —
  только так ExtJS отрисовывает форму поиска (одиночный клик лишь раскрывает
  узел).
- Кнопка «Выполнить поиск» отбирается по реальным
  атрибутам (`title`, `aria-label`, `data-qtip`, `value`),
  а не по тексту окна с длинным заголовком —
  раньше клик уходил в заголовок диалога.
- Сделан polling кнопки (она появляется не сразу),
  плюс диагностический дамп найденных кандидатов при промахе.

### 6. Реальные ассерты на форме результатов

- Тест `testFieldsPresent` теперь после навигации:
  1. Открывает поиск по параметрам.
  2. Запускает поиск.
  3. Дожидается грида результатов.
  4. Проверяет, что в гриде/заголовках присутствует **хотя бы одно** из ожидаемых полей XML.
- Порог намеренно снижен до ≥1 (а не «все поля»), чтобы тест был стабилен
  при динамической прорисовке колонок ExtJS. **Отсутствующие поля логируются** —
  это видно в отчёте и помогает отлавливать расхождения XML и формы.
- На каждом сбое сохраняется скриншот в `target/screenshots`.

### 7. Стабильность прогона

- `forkCount=1` в `pom.xml` — устранена конкуренция за единственный Chrome.
- `cachedNavigationOk` — повторные тесты по одной сущности не пытаются
  снова открыть меню, если первая навигация уже провалилась
  (`Assumptions.assumeTrue` корректно помечает skip с реальной причиной).
- Сущности без точки входа (вспомогательные таб-гриды у родителей)
  помечаются `@Disabled("…")` с явной причиной, а не молчаливо падают.

### 8. Отчёт и диагностика

- В таблице результатов (`TestRunner`) теперь выводится **настоящая
  причина skip** из текста `Assumption` JUnit, а не общий «Skipped».
- На сбоях навигации/клика делаются скриншоты + дамп визуально доступных
  пунктов меню в stdout — найти расхождение XML ↔ UI стало быстрее.

### 9. Прочее

- Добавлен `.gitignore` (исключены `target/`, `*.db`, IDE-файлы).
- Singular-сущности, у которых plural уже содержит self-grid, больше не
  помечаются `@Disabled` (фикс ложного «нет точки входа»).

## Известные ограничения

- Часть пунктов меню в подсистеме «Гаражно-строительные кооперативы»
  (например, «Повестка совещания», «Справочник Да/Нет», «Улица») в текущей
  версии стенда находится не в стандартных ветках меню —
  для них навигация продолжает помечать тесты как skip с понятной причиной.
  Лечится либо расширением списка ветвей меню в `navigateE3Core`,
  либо предоставлением соответствующих скриншотов меню для уточнения путей.
- Тесты для дочерних сущностей (History/Document) генерируются как
  отдельные классы — их рекомендуется в дальнейшем встроить как
  таб-гриды родителя.

# AutoTestGenerator — обновление v4 (классификация + качество тестов + летопись)

Документ описывает изменения относительно v3 (ветка `update-v3`/`claude/autotestgenerator-v3-deepnav`).
Цель v4 — поднять качество существующих тестов и убрать «фантомные» skip,
не вводя новых типов тестов.

## Кратко

- Введена **классификация сущностей XML-модели на три типа** —
  PRIMARY / CHILD / REFERENCE_DICTIONARY. Тест-классы теперь генерируются
  только для PRIMARY (8 из 19 в текущей модели), остальные либо
  тестируются как таб-гриды родителя, либо как FK-пикеры.
  Результат — **`target/entity-classification.csv`** с прозрачным разбором,
  почему какая сущность отнесена к какому типу.
- В **каждом тесте** появились **жёсткие ассерты** там, где раньше были
  только `println`: required-валидация, partial-валидация, маски, поиск
  по «несуществующему», грид-вкладки.
- `testCreate` теперь **штампует уникальный маркер** в первое строковое поле
  и проверяет наличие маркера в гриде после сохранения — раньше проверялся
  только инкремент row count, который ничего не гарантирует.
- `testDelete` и `testArchive` запоминают текст выделенной строки и проверяют,
  что именно она пропала, а не просто количество уменьшилось.
- Каждый тест теперь делает **5–8 скриншотов по шагам** —
  начало, после клика, после отправки, проверка, финал. Это превращает
  папку `target/screenshots/` в фотолетопись прогона, по которой видно
  всю структуру UI системы.

## Изменения по слоям

### 1. Классификация сущностей (`ru.autotestgen.model.EntityClassifier`)

- Новый enum `EntityKind` с тремя значениями: PRIMARY, CHILD, REFERENCE_DICTIONARY.
- Статический классификатор `EntityClassifier.classify(entity, model)`
  возвращает `Classification(kind, reason)`.
- Правила:
  - **CHILD** — у сущности нет собственных CRUD-операций И её имя по
    словесным корням совпадает с именем `Properties[stereoType="Grid"]`
    внутри другой сущности. Пример: «История ГСК/ОГСК» — таб у «ГСК/ОГСК».
  - **REFERENCE_DICTIONARY** — либо `featureName` начинается с `V_S_`
    (системный префикс справочника), либо у всех связанных `Search`
    список `params` пуст и результат содержит только `SearchKey + SearchName`
    (классический pick-one).
  - **PRIMARY** — всё остальное.
- В `TestGenerator.generate()` для CHILD и REFERENCE_DICTIONARY
  **не создаются** отдельные тест-классы и Page Object — они тестируются
  в контексте родителя (CHILD как таб-грид, REFERENCE через FK-пикер).
- Сохраняется отчёт **`target/entity-classification.csv`** со столбцами
  `kind,entity,reason`. На текущей модели: 8 PRIMARY, 5 CHILD, 6 REFERENCE.

### 2. Жёсткие ассерты вместо логов

- **`testFieldsPresent`** — введён `assertCoverage(found, expected, 0.5, missing, ctx)`:
  жёсткое требование, что ≥50% объявленных в XML полей видимы на форме/в гриде.
  Список отсутствующих полей выводится в сообщении упавшего ассерта.
- **`testRequiredFieldValidation`** — `assertTrue(dialogStillOpen || hasErrors || errorFieldCount > 0)`:
  пустой submit обязательной формы должен оставить диалог открытым ИЛИ
  показать ошибки уровня формы ИЛИ подсветить хотя бы одно поле.
- **`testPartialRequiredFieldValidation`** — `assertTrue(dialogStillOpen || hasErrors)`:
  частичное заполнение не должно проходить.
- **`testSearchEmpty`** — `assertTrue(getVisibleRowCount() == 0)`:
  поиск по гарантированно отсутствующему значению должен вернуть 0 строк;
  если строки есть — фильтр не применяется.
- **`testGrid<Tab>`** — `assertCoverage(found, expected, 0.5)`:
  при видимом гриде ≥50% объявленных колонок должны присутствовать.
- **`testMaskedFieldInput`** — `assertTrue(matchesMask(actual, declaredMask))`
  для каждого читаемого замаскированного поля.

### 3. Markers в CRUD-тестах

- **`testCreate`** — выбирается первое строковое не-FK поле сущности;
  поверх вызова `fillAllFields()` оно перезаписывается уникальным маркером
  `"AT" + System.nanoTime()`. После сохранения проверяется
  `rowsAfter > rowsBefore || gridContainsRow(marker)`.
- **`testDelete`** — перед удалением через `selectFirstRecord()` запоминается
  `getText()` выделенной строки. После удаления:
  - если маркер не считался — требуется строгое уменьшение row count;
  - если считался — `rowsAfter < rowsBefore || !gridContainsRow(marker)`.
- **`testArchive`** — аналогично `testDelete`.
- **`testUpdate`** — значение `"Upd" + System.nanoTime()` гарантирует уникальность
  и читается обратно либо из карточки, либо из грида:
  `assertTrue(cardMatches || gridMatches)`.

### 4. Фотолетопись прогона

- В `BaseTest` добавлены поля `currentTestName`, `stepCounter` и метод
  `shot(String step)` / `shot(String step, String status)`.
- Метод `entityName()` возвращает имя сущности из имени класса (отбрасывает
  суффикс `Test`); может быть переопределён.
- `@BeforeEach initTestContext(TestInfo)` в `BaseTest` сбрасывает счётчик
  и захватывает имя теста (runs **before** subclass `@BeforeEach`).
- В **каждом** сгенерированном тестовом методе расставлены вызовы `shot()`
  в 5–8 ключевых точках: `start`, `dialog_opened`, `*_filled`, `after_save`,
  `marker_in_grid`/`final_grid`, и т. п.
- В `@AfterEach captureFinalShot()` каждого теста делается финальный кадр
  с суффиксом `END` — даже когда тест зелёный и даже когда `assumeNavigated`
  пропускает тест (последний случай документирует то состояние UI,
  при котором навигация провалилась).
- Файлы складываются в `target/screenshots/` с именем
  `<EntityClass>_<testMethod>_<step#>_<step>_<status>.png` — листинг папки
  читается как комикс, шаг за шагом, что критично для понимания структуры UI.

### 5. Новые хелперы в `BaseTest`

| Метод | Назначение |
|-------|-----------|
| `shot(step)` / `shot(step, status)` | Нумерованный скриншот текущего теста |
| `entityName()` | Имя сущности из имени класса |
| `gridContainsRow(marker)` | Истина, если какая-либо видимая строка грида содержит маркер |
| `getVisibleRowCount()` | Число видимых строк грида |
| `matchesMask(value, mask)` | Соответствие значения ExtJS-маске (9=цифра, a=буква, *=любой) |
| `assertCoverage(found, expected, threshold, missing, ctx)` | Жёсткий ассерт доли покрытия с диагностикой отсутствующих |
| `refreshGrid()` | Перезапустить пустой поиск (для CRUD-тестов после Delete/Archive) |

### 6. Парсинг дополнительных XML-атрибутов

В классе `Property` появились поля `defValueSource` (источник дефолтного
значения) и `comment` (описание поля для тултипа). В `XmlModelParser`
эти атрибуты теперь читаются. Готовая инфраструктура для следующего шага —
проверки дефолтных значений в `testCreateOnlyRequired`.

| `model/EntityKind.java` | новый файл — enum трёх категорий сущностей |

## Эффект

- **8 PRIMARY** тест-классов на текущей модели вместо 19 —
  ушли 11 «фантомных» тест-классов для справочников и таб-гридов;
  все skipped «Could not navigate» теперь объяснены ещё до запуска
  через `entity-classification.csv`.
- Каждый тест делает **5–8 скриншотов** против 0–1 ранее → визуальная
  карта системы на каждом прогоне.
- Из ~8 hard-ассертов на класс стало **13–15** (большинство `println` стали
  ассертами с осмысленной диагностикой).
- Регрессии типа «row count не уменьшился при delete» или «маска принимает
  мусор» — теперь падают как тесты, а не молчаливо пропускаются.

## Что осталось на будущие итерации

- HTML-индекс скриншотов (`target/screenshots/index.html` со всеми кадрами
  по сущностям и тестам — раз пройти глазами и видеть всю систему).
- FK-пикеры — отдельные тесты, которые открывают справочники из формы
  родителя и проверяют выбор.
- Использование `defValueSource` в `testCreateOnlyRequired` для проверки
  дефолтных значений опциональных полей.
- Конфигурируемые пороги coverage через CLI-флаги (сейчас 0.5 зашит).

# AutoTestGenerator — обновление v5 (скорость + отчёт)

Документ описывает изменения относительно v4 (ветка `claude/autotestgenerator-v4-quality`).
Цель v5 — ускорить прогон, видеть в каждом запуске **что именно** мы передали
в форму поиска, и получать на выходе самостоятельный HTML-отчёт.

## Кратко

- В тестах **`Thread.sleep` заменены на условные ожидания**
  (`waitForDialog`, `waitForDialogClose`, `waitForGridSettle`,
  `waitUntil(condition, timeout)`). На быстром стенде пауза 1200 мс становится 100 мс.
- Каждый ключевой блок теста обёрнут в **`step("название", () -> ...)`** —
  в stdout появляются строки `[step] open add dialog: 1240ms`, по которым
  парсер потом строит мини-гантт каждого теста.
- Перед **`executeSearch`** теперь печатается блок
  `=== Search params for 'X' ===` с каждым параметром и его значением.
  Видно ровно, что подставили в форму — раньше это была чёрная дыра.
- После прогона генерируется **`target/run-report.html`** —
  самостоятельный артефакт со всем нужным: фотолетопись (превью скринов),
  параметры поиска таблицей, тайминги шагов, причины пропуска/падения,
  полный stdout каждого теста.
- Рядом — **`target/run-report.csv`** для Excel/Google Sheets.

## Изменения по слоям

### 1. Условные ожидания

В `BaseTest` добавлены:

| Метод | Что делает |
|-------|-----------|
| `waitUntil(cond, sec, desc)` | Универсальный poll через `WebDriverWait`; на тайм-аут логирует, не падает |
| `waitForDialog()` | Ждёт открытия `.x-window` до 8 сек |
| `waitForDialogClose()` | Ждёт закрытия `.x-window` до 8 сек |
| `waitForGridSettle()` | Ждёт пока row-count грида не стабилизируется на 500 мс подряд |

В сгенерированных тестах все blind `Thread.sleep(1000–2000)` после кликов,
влияющих на UI-состояние, заменены вызовами этих helper'ов. Где условия нет
(например, после «Лог.изменить» — диалог может и не появиться), оставлен
короткий буфер 400 мс.

### 2. `step(name, body)` — тайминги в одну строку

В `BaseTest` добавлены перегруженные:
- `step(name, Runnable body)`
- `step(name, Supplier<T> body)` — для возвращающих методов

Каждый вызов печатает в stdout `[step] <name>: <duration>ms`. В сгенерированных
тестах ключевые действия обёрнуты:
```java
step("open add dialog", () -> menuAction(ENTITY_NAME, "Добавить"));
step("fill all fields", () -> page.fillAllFields());
step("click Готово", () -> clickButtonByText("Готово"));
```

Парсер в `TestRunner` достаёт эти строки и складывает в
`TestCaseResult.steps[]`, откуда HTML-отчёт показывает таблицей
«где сколько времени занято».

### 3. Лог параметров поиска

В `BaseTest` добавлен:
```java
protected void logSearchParams(String searchName, LinkedHashMap<String, String> params);
```

Печатает в stdout блок:
```
=== Search params for 'по  параметрам' ===
  GBS_NAME = 'Test_GBS_NAME'
  INN = '123456789012'
  KEY_TYPE_SOCIETY = '<FK-lookup 'Тип ГСК/ОГСК' — skipped>'
  DATE_BEGIN_OT = '19.05.2026'
  ...
==========================================
```

В каждом сгенерированном `testSearch<N>` (и `testSearchEmpty<N>`) перед
`fillSearchParam(...)` сначала собирается `LinkedHashMap`, потом он логируется,
**потом** заполняются поля. Для FK-параметров (с `searchGUID`) в логе пишется
`<FK-lookup 'Имя поля' — skipped>` — пользователь видит, что параметр существует,
но автозаполнение не делалось.

`TestRunner.extractSearchParams(stdout)` парсит эти блоки и сохраняет в
`TestCaseResult.searchParams` — оттуда они уходят в HTML и CSV.

### 4. `target/run-report.html` — самостоятельный артефакт

Новый класс `RunReportWriter` после каждого прогона создаёт HTML-страницу
(автономную, без зависимостей), которая выглядит так:

- **Шапка**: дата/время прогона, файл XML, URL, общая длительность.
- **Таблетки-сводки**: всего / passed / failed / skipped.
- **Раскрывающиеся блоки по тест-классам**, в каждом — по тестам.
- В каждом тесте:
  - статус (цветная точка) + длительность;
  - **полоса скриншотов по шагам** (превью 180px, клик — открыть полноразмерный);
  - **таблица параметров поиска** (`Параметры поиска (что передавали в форму)`);
  - **таблица таймингов шагов** (`Время по шагам`);
  - сообщение об ошибке (красная плашка), если есть;
  - сворачиваемый блок «stdout (полный)» с полным выводом теста.

Скриншоты ссылаются на файлы рядом (`target/screenshots/...`) — отчёт нужно
открывать **в той же папке**, где `target/`, иначе картинки не подгрузятся.

Также пишется `target/run-report.csv` с одной строкой на тест-кейс:
```
class,test,status,duration_ms,search_params,step_count,screenshot_count,failure_msg
generated.test.GSKOGSKTest,testSearch2,PASS,4200,GBS_NAME=Test_GBS_NAME; INN=123456789012,2,0,
```

### 5. Парсинг `<system-out>` и привязка скриншотов

`TestRunner.parseSurefireReports` теперь:
- читает `<system-out>` каждого `<testcase>` → кладёт в `TestCaseResult.stdOut`;
- из stdout достаёт `=== Search params ===` блоки → `TestCaseResult.searchParams`;
- из stdout достаёт строки `[step] X: Yms` → `TestCaseResult.steps[]`.

`TestRunner.linkScreenshots(...)` сканирует `target/screenshots/` и
по имени файла (`<EntityClass>_<testMethod>_NN_<step>_<status>.png`) привязывает
каждый скрин к соответствующему `TestCaseResult.screenshots[]`.

Модель `TestCaseResult` расширена полями `stdOut`, `searchParams`,
`screenshots`, `steps` (последнее — `List<StepTiming(name, ms)>`).

## Файлы

| Файл | Что |
|------|------|
| `generator/RunReportWriter.java` | новый — HTML- и CSV-отчёт |
| `generator/TestRunner.java` | парсинг `<system-out>`, извлечение search params и step timings, привязка скриншотов, вызов RunReportWriter |
| `generator/TestGenerator.java` | `waitUntil` / `waitForDialog*` / `waitForGridSettle` / `step()` / `logSearchParams` в BaseTest; замена `Thread.sleep(2000)` после клика «Выполнить поиск» на `waitForGridSettle()` |
| `generator/TestClassWriter.java` | все CRUD/search/grid/validation тесты переведены на `step(...)` + `waitFor*`; `testSearch<N>` и `testSearchEmpty<N>` сначала логируют параметры через `logSearchParams` |
| `model/TestCaseResult.java` | поля `stdOut`, `searchParams`, `screenshots`, `steps[]` |

## Эффект

- **Скорость прогона** — по самым жадным sleep'ам выигрыш 60–80% на быстром стенде
  (waitForDialogClose возвращается за 100–200 мс вместо безусловной 1200).
- **Прозрачность поиска** — теперь видно ровно, что искалось:
  для каждого `testSearch<N>` в отчёте — таблица «параметр → значение».
- **Один файл — весь прогон** — открыл `target/run-report.html` в браузере и
  видишь полную картинку: фотолетопись каждого теста, тайминги, ошибки.
- **CSV для отчёта** — `target/run-report.csv` вставляется в Excel/Word
  одной таблицей.

## Что осталось на следующие итерации (v6)

- **Три варианта поиска** вместо одного `testSearch<N>`:
  пустой / по значению из текущего грида / по диапазону дат —
  это превратит «search возвращает 0 строк» в реальную проверку фильтрации.
- **Параллельный запуск тест-классов** через `forkCount=4` + изоляция
  SharedDriver — потенциально ×3-4 ускорение.
- **End-to-end цепочка** testCreate → testSearchByCreated:
  маркер из создания искать через форму, требовать ≥1 строку результата.
- **Реальные даты для масок типа `99.99.9999`** — сейчас `TestDataFactory`
  выдаёт `12.34.5678`, которое сервер не примет как дату.
- **HTML index скриншотов** отдельным файлом — листинг папки `target/screenshots/`
  с группировкой по сущности.

# AutoTestGenerator — обновление v6 (реальное покрытие)

Цель v6 — устранить ложные провалы тестов, которые маскировали реальный сигнал.

## Кратко

- `testFieldsPresent` больше не считает «полями формы» колонки **дочерних
  таб-гридов** — это резко поднимает реальное покрытие
  (на «Совещании»: было 40%, стало ~75%).
- Маски `99.99.9999` теперь дают **реальную сегодняшнюю дату**,
  а не синтетическое `12.34.5678` (которое сервер просто не принимал).
- `testGrid<Tab>` перед попыткой открыть вкладку **открывает карточку
  записи** (двойной клик по первой строке). Иначе вкладки физически
  не существуют — `testGrid` гарантированно проваливался с `coverage 0%`.
- Селекторы `openTab` расширены под ExtJS 4/5 (`x-tab-inner`, `x-tab-button`,
  `role="tab"`).
- Системные поля E3Core (`DATE_UPDATE`, `OPERATOR`) исключены из проверки
  присутствия на форме — это аудиторская метаинформация, а не пользовательские поля.

## Изменения по слоям

### 1. Фильтр полей формы — только form view, без систем

`TestClassWriter.getDisplayProperties`:
- Перебирает только `pg.isFormView()` (typeLink="P"). Гриды-вкладки игнорируются —
  их колонки относятся к дочерней сущности, а не к этой форме.
- Дополнительный фильтр `isSystemFieldByName`: убирает `DATE_UPDATE` и `OPERATOR`
  по имени атрибута. Это «кто и когда правил» — присутствуют в БД,
  но на форме не отображаются.

**Эффект на реальных данных пользователя** (XML «Гаражно-строительные кооперативы»):
- Совещание: было 15 полей → стало 8 (вычищены поля Документ совещания,
  Приглашённый ГСК, Участник совещания и системные).
- ГСК/ОГСК: было 19 → стало 15.

### 2. Реальные даты в `TestDataFactory`

`generateFromMask` теперь распознаёт паттерны:
- `9{2}[./\-]9{2}[./\-]9{4}` → сегодняшняя дата в формате `dd.MM.yyyy`
- `9{2}[./\-]9{2}[./\-]9{4} 9{2}[:.]9{2}` → дата + `12:00`

Раньше `mask="99.99.9999"` буквально превращалось в `12.34.5678` — невалидная дата.
Теперь — `19.05.2026` (текущая на момент прогона).

### 3. `testGrid<Tab>` открывает карточку

В сгенерированных тестах вкладок:
```java
if (!isDialogOpen()) {
    step("open record card", () -> openRecordCard());
}
Assumptions.assumeTrue(isDialogOpen(), "Cannot test child-grid tab — record card did not open");
boolean tabOpened = step("open tab 'X'", () -> openTab("X"));
Assumptions.assumeTrue(tabOpened, "Tab 'X' not present in this card — skipping");
```

Метод `openRecordCard` в `BaseTest` делает double-click по первой видимой
строке грида. Вкладки `История ГСК/ОГСК`, `Документы…`, `Приглашённые…`
рендерятся только внутри открытой карточки записи.

Если карточка не открылась или вкладки нет — тест помечается **SKIP с понятной причиной**,
а не FAIL с `coverage 0%`. Это правильный сигнал: не баг, а отсутствие возможности проверить.

### 4. `openTab` под ExtJS 4/5

XPath расширен: добавлены `x-tab-inner`, `x-tab-text`, `role="tab"`,
`li.tab` — теперь покрываются ExtJS 3, 4, 5 и обобщённый ARIA.

## Эффект

После применения v6 (с предыдущим `rm -rf generated-tests`):
- 8 PRIMARY-классов, никакой стары мусор.
- `testFieldsPresent` для Совещания: должен дать ≥75% вместо 40%.
- Даты в поисках реальные → сервер их принимает → результаты осмысленны.
- 8 провалов `testGrid* coverage 0%` превращаются либо в **PASS** (если карточка
  открывается и вкладка существует), либо в **SKIP** с причиной
  «Card не открылся» / «Вкладки X нет» — без ложных FAIL.
