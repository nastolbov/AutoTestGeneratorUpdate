## 1.7. Выбор стратегии тестирования, разработка тестов, программа и методика испытаний

В данном разделе представлены стратегия, программа и методика испытаний разработанной информационной системы. Программа и методика испытаний составлены в соответствии с ГОСТ 19.301-79 [24].

### 1.7.1. Объект и цель испытаний

Объектом испытаний является информационная система автоматической генерации UI-автотестов веб-приложений на платформе E3Core (AutoTestGenerator), а также порождаемый ею Maven-проект автотестов.

Цели испытаний:
- проверка соответствия разработанной программы требованиям, изложенным в техническом задании (Приложение 1);
- выявление и устранение ошибок, допущенных при реализации;
- подтверждение работоспособности системы на эталонной XML-метамодели подсистемы E3Core.

### 1.7.2. Требования к информационному, аппаратно-программному обеспечению

#### 1.7.2.1. Требования к функциональным характеристикам

Программа представляет собой настольное приложение на языке Java SE 17 [22] с графическим интерфейсом на JavaFX 24 [16] и реализует следующие функции:

- разбор XML-метамодели формата E3Core с использованием потокового парсера StAX [20] и поддержкой трёх XML-неймспейсов (`NS_E`, `NS_E3`, `NS_MD`);
- транслитерация русских имён сущностей в валидные Java-идентификаторы;
- классификация сущностей модели на три категории: PRIMARY (основная), CHILD (дочерняя), REFERENCE_DICTIONARY (справочник);
- генерация Maven-проекта автотестов: `pom.xml`, общие классы (`SharedDriver`, `BaseTest`, `TestData`), Page Object [21] и тестовый класс на JUnit 5 [17] для каждой PRIMARY-сущности;
- поддержка трёх уровней тестов: SMOKE (только `testFieldsPresent`), BASIC (+ `testSearch*`, `testGrid*`), FULL (+ полный CRUD-цикл и тесты валидации);
- запуск сгенерированных тестов через `mvn test` [15] с потоковым выводом и тайм-аутом 10 минут;
- параллельный режим запуска (`fastMode`) — три параллельных headless-экземпляра Chrome через `-DforkCount=3 -Dheadless=true`;
- выборочный запуск подмножества тестов через формирование Surefire-фильтра `-Dtest=...`;
- сбор результатов из XML-отчётов Surefire через потоковый StAX-парсер;
- сохранение истории прогонов в локальную базу данных SQLite [19];
- отображение истории прогонов в графическом интерфейсе;
- формирование пользовательского HTML-отчёта с фотолетописью (скриншоты на каждом шаге теста) и CSV-выгрузки.

#### 1.7.2.2. Требования к надёжности

К разрабатываемому программному обеспечению предъявляются следующие требования к надёжности:

- система должна иметь защиту от некорректных действий оператора и ошибочных исходных данных;
- при возникновении ошибки разбора XML система должна формировать исключение `ParserException` с понятным сообщением и не завершаться аварийно;
- сохранение результатов прогона в локальную базу данных должно выполняться в рамках одной транзакции с откатом при ошибке;
- при сбое записи в базу данных программа должна продолжить работу без сохранения истории (graceful degradation), уведомив пользователя;
- при отсутствии установленных вспомогательных средств (Apache Maven, Google Chrome) программа должна выводить понятное сообщение об ошибке при попытке прогона тестов;
- все открытые файловые потоки и JDBC-соединения должны освобождаться через конструкцию try-with-resources;
- локальная база данных истории прогонов должна сохраняться между запусками и автоматически создаваться при первом запуске.

#### 1.7.2.3. Требования к составу и параметрам технических средств

Компьютер, на котором будет установлена система, должен обладать следующими характеристиками:

- процессор с тактовой частотой не менее 2 ГГц;
- объём оперативной памяти не менее 4 ГБ (рекомендуется 8 ГБ);
- объём свободного пространства на жёстком диске не менее 2 ГБ;
- монитор, поддерживающий разрешение не менее 1024×768 точек;
- сетевой адаптер для подключения к тестируемому веб-приложению по HTTP/HTTPS;
- установленный JDK Java SE 17 или новее;
- установленный Apache Maven версии 3.8 и выше;
- установленный браузер Google Chrome актуальной версии.

### 1.7.3. Состав, порядок и методы испытаний

Тестирование разработанного программного обеспечения проводилось согласно следующему составу мероприятий:

- проверка программной документации на соответствие требований ЕСПД методом ручного контроля;
- автономное тестирование разработанных модулей;
- комплексное тестирование межмодульных интерфейсов;
- системное тестирование программы на соответствие функциональным требованиям и требованиям к надёжности, изложенным в техническом задании (Приложение 1).

Тестирование проводилось на персональном компьютере, имеющем следующие характеристики:

- процессор Intel Core i5-12400 (6 ядер, 12 потоков, тактовая частота до 4,4 ГГц);
- объём оперативной памяти 16 ГБ;
- твердотельный накопитель объёмом 512 ГБ;
- операционная система Microsoft Windows 11;
- монитор с разрешением 1920×1080.

Для тестирования программной документации использовался **метод ручного контроля**. Ручной контроль применяется на ранних этапах разработки, поскольку с его помощью можно обнаружить от 30 до 70 % ошибок логического проектирования и кодирования. Исходными данными для таких проверок являются: техническое задание, разработанная программная документация, диаграммы, текст программы.

Из методов ручного контроля выбран **метод проверки за столом**. Метод не требует наличия группы специалистов: проверка исходного текста и документации проводится одним человеком, который последовательно читает текст программы и сверяет его на наличие возможных ошибок по списку наиболее часто встречающихся.

Для тестирования программного обеспечения использовалось **автономное, комплексное и системное тестирование**. Для автономного тестирования модулей выбран один из методов функционального тестирования — **метод граничных значений** [12]. Исходными данными для этого метода являются: программные модули, спецификации на компоненты, корректные и некорректные данные для модулей.
