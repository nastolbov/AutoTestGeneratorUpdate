# Защита: что делает каждый класс + ответы на вопросы (AutoTestGenerator)

Шпаргалка для защиты и ответов комиссии. Всё выверено по коду `ru.autotestgen.*`.

---

## A. Что делает каждый класс (для диаграммы пакетов, слайд 9)

Архитектура слоистая: **UI → Parser → Model → Generator → Data**, плюс общий **Common**. Одна фраза на класс — этого достаточно для защиты.

### Пакет `ui` — графический интерфейс (JavaFX)
- **App / Launcher** — точка входа, запуск JavaFX-приложения и главного окна.
- **MainController** — контроллер главного окна: обрабатывает кнопки (разобрать XML, сгенерировать, запустить, история), собирает параметры и связывает все подсистемы.

### Пакет `parser` — чтение XML-метамодели
- **XmlModelParser** — главный парсер: потоково (StAX) читает XML и собирает объектную модель `AppModel`; делегирует разбор частей специализированным парсерам.
- **EntityParser** — разбирает элемент `<Object>` (сущность): её свойства и ассоциации.
- **PropertyGroupParser** — разбирает группы свойств (`<Properties>`): поля (`Property`) и операции (`Operation`: CRUD, архив и т.п.).
- **SearchParser** — разбирает блок поисков (`<Searches>`): параметры и колонки результата.
- **StaxUtils** — утилиты безопасного чтения атрибутов (нет атрибута → «», нечисло → 0).
- **XmlNamespaces** — константы XML-пространств имён (NS_E, NS_E3, NS_MD).

### Пакет `model` — структуры данных предметной области (в памяти)
- **AppModel** — корень модели: список сущностей и поисков, имя подсистемы.
- **EntityObject** — одна сущность (имя, ключ, группы свойств, операции, ассоциации).
- **EntityKind** — перечисление категорий: `PRIMARY` / `CHILD` / `REFERENCE_DICTIONARY`.
- **EntityClassifier** — **логика классификации**: определяет, к какой категории отнести сущность.
- **PropertyGroup, Property, Operation, Modifier, Association, Search, SearchParam, SearchResult, AttrType, ModifyType** — классы-контейнеры (поля, операции, связи, поиски, типы) — «слепок» структуры приложения.
- **TestRunResult, TestCaseResult** — результаты прогона (для слоя данных/отчётов).

### Пакет `generator` — генерация и запуск тестов
- **TestGenerator** — оркестратор: по модели создаёт весь Maven-проект (pom.xml, инфраструктуру, классы).
- **PageObjectWriter** — пишет классы **Page Object** для каждой сущности.
- **TestClassWriter** — пишет **тест-классы JUnit 5** (сами сценарии-проверки).
- **TestDataFactory** — подбирает тестовые значения по типу поля и маске.
- **TestConfig** — параметры генерации/запуска (URL, логин, каталог, режим).
- **TestRunner** — запускает `mvn test`, собирает отчёты Surefire.
- **RunReportWriter** — формирует пользовательские отчёты HTML (с фотолетописью) и CSV.

### Пакет `data` — хранение истории прогонов (SQLite)
- **DatabaseConnection** — открытие соединения с SQLite.
- **SchemaInitializer** — создаёт таблицы при первом запуске (`CREATE TABLE IF NOT EXISTS`).
- **TestRunDao** — запись/чтение прогона (таблица `test_run`).
- **TestCaseDao** — запись/чтение результатов тестов (таблица `test_case`).
- **ReportDao** — фасад: сохранить прогон / получить историю (одна транзакция).

### Пакет `common` — общие утилиты
- **Transliterator** — русские имена → корректные Java-идентификаторы.
- **JavaFileWriter** — форматированная запись `.java` (отступы, блоки).
- **ParserException** — единый тип ошибки разбора.

## B. Ответы на ваши вопросы (простым языком — так и говорите)

### 1. Что такое Model, Parser и Data?
Это три слоя с разной ответственностью:
- **Parser** — слой **чтения**: «переводит» XML-метамодель в объекты Java.
- **Model** — слой **данных в памяти**: набор классов-контейнеров, описывающих приложение (сущности, поля, операции, поиски) + правило классификации. Это «то, что система знает о тестируемом приложении».
- **Data** — слой **хранения**: сохраняет историю прогонов в локальную БД SQLite (через DAO).

Коротко: **Parser наполняет Model, Generator читает Model и создаёт тесты, Data хранит результаты.**

### 2. Как по сути работает наш парсер?
Используется **потоковый разбор StAX** (Streaming API for XML):
1. `XmlModelParser` открывает файл и идёт по XML **событиями** (начало/конец элемента), не загружая весь документ в память.
2. Встретив `<Object>` — передаёт управление `EntityParser` (тот внутри: `<Properties>` → `PropertyGroupParser` → поля и операции; `<AssociationObjectA>` → ассоциации).
3. Встретив `<Searches>` — передаёт `SearchParser`.
4. Атрибуты читаются через `StaxUtils` безопасно (нет атрибута → пустая строка, не падает).
5. На выходе — заполненная объектная модель `AppModel`.

**Почему StAX, а не DOM:** DOM строит всё дерево в памяти — дорого для крупной метамодели; StAX читает последовательно и экономит память. Поддерживаются три пространства имён (NS_E, NS_E3, NS_MD).

### 3. Что такое Page Object?
**Page Object — паттерн проектирования автотестов**: на каждую страницу/форму приложения заводится отдельный класс, который прячет внутри **локаторы элементов** (как найти поле/кнопку) и **действия** (заполнить поле, нажать «Сохранить»).
- Тест **не знает** про CSS/XPath — он вызывает понятные методы: `page.fillНаименование("...")`, `page.clickSave()`.
- У нас классы `<Сущность>Page.java` генерирует `PageObjectWriter`: поля-локаторы по свойствам сущности + методы `fill*/get*`, `fillAllFields`, `clearForm`, `isFieldDisplayed`.
- **Плюс:** при изменении вёрстки правишь один Page Object — все тесты продолжают работать.

### 4. Где мы задаём тестовые сценарии?
Сценарии **не пишутся руками** — их **порождает `TestClassWriter`** в виде методов тест-класса `<Сущность>Test.java`. Каждый метод (`@Test @Order(n)`) — это сценарий:
- `testFieldsPresent` — наличие полей формы;
- `testRequiredFieldValidation` (+ частичная) — валидация обязательных;
- `testCreate / testUpdate / testDelete` — CRUD;
- `testLogicalEdit / testArchive` — если у сущности есть такие операции;
- `testSearchN` — параметрические поиски;
- `testGrid…` — проверка гридов/вкладок.

То есть «где задаём сценарии»: **в правилах генерации `TestClassWriter`**, а **какие именно** сценарии создавать — диктует **модель** (операции CRUD, поиски, гриды берутся из метамодели). Изменилась модель — перегенерировали — набор сценариев обновился сам.

### 5. Как реализована логика переходов вкладок?
Это нужно для **дочерних (CHILD)** сущностей: их данные лежат на **вкладке-гриде внутри карточки родителя**. Сгенерированный тест в `@BeforeEach` делает три шага (с ретраем до 3 попыток):
1. `navigateToEntity(родитель)` — открыть список родителя;
2. `selectAndOpenRecord()` — открыть карточку записи;
3. **`openTab(TAB_NAME)`** — переключиться на нужную вкладку.

Метод **`openTab`** (в базовом классе `BaseTest`) находит элемент таб-стрипа **ExtJS** по названию вкладки (для ExtJS 3 — класс `.x-tab-strip-text`, для 4/5 — `.x-tab-inner`), либо узел левого дерева внутри карточки, и кликает. Клик пробуется несколькими способами (обычный Selenium-клик → `Actions` → JS-клик → вызов ExtJS API), потому что ExtJS-гриды не всегда реагируют на синтетический клик. После перехода тест выполняет проверки грида/CRUD на этой вкладке.

### 6. Зачем пакет Common?
Это **общие утилиты, нужные сразу нескольким пакетам** (parser, model, generator):
- `Transliterator` — преобразование русских имён в Java-идентификаторы;
- `JavaFileWriter` — аккуратная запись генерируемого Java-кода (отступы, блоки);
- `ParserException` — единый тип ошибки разбора.

Их вынесли отдельно, чтобы **не дублировать код** и **избежать циклических зависимостей** между слоями: общий пакет зависит ни от кого, а от него зависят остальные.

## C. Как объяснять диаграмму пакетов на защите (30–40 сек)
«Архитектура слоистая. **UI** принимает команды пользователя. **Parser** читает XML-метамодель в объектную **Model**. **Generator** по модели создаёт Page Object и тест-классы, запускает их и формирует отчёты. **Data** хранит историю прогонов в SQLite. **Common** — общие утилиты для всех слоёв. Зависимости направлены сверху вниз, без циклов — это и обеспечивает слабую связанность.»
Дальше — если спросят — раскрываете конкретный класс по списку выше.
