# AutoTestGenerator — памятка по системе

Краткий, но полный путеводитель: как программа разбирает модель, что генерирует, как ищет родителей, как ходит по меню, заполняет формы и формирует отчёты.

---

## 1. Программа в одной фразе

**Из XML-модели приложения E3Core строим готовый Maven-проект на Java + Selenium + JUnit, который запускается одной командой и формирует HTML-отчёт со скриншотами по каждому шагу.**

Полный поток выполнения:

```
XML-модель  →  парсер  →  объектная модель  →  классификатор  →
            →  генератор (Java + Maven)  →  Maven прогон тестов в Chrome  →
            →  сбор результатов  →  HTML/CSV-отчёт + SQLite-БД
```

---

## 2. Парсер (`XmlModelParser`)

Читает XML потоково через стандартный StAX. Из дерева вытаскивает шесть типов объектов:

| XML-элемент | Что это | Что забираем |
|---|---|---|
| `<e:Object>` | Бизнес-сущность | `name`, `keyName` (имя PK-колонки в БД), `featureName` (имя view), `nameValueMethod` |
| `<e3:AssociateItem>` | Внешний ключ (ассоциация) | `associateItemGuid`, `searchGuid`, `role_A`/`role_B` (направление) |
| `<e:Properties>` | Группа свойств (форма или грид) | `stereoType` (`Form` / `Grid`), `typeLink` (`P` = карточка), `name`, `flag_display` |
| `<e:Property>` | Поле сущности | `name` (русское), `attrName` (техническое), `attrType` (STRING/DECIMAL/DATE/DATETIME), `mask`, `necessarily`, `flag_display`, `defValueSource`, `comment` |
| `<e3:Search>` | Поиск (запрос) | `name`, `searchObjectGuid`, список `params` и `result` |
| `<e:Operation>` + `<e:Modifier>` | Операции CRUD | какие действия доступны: INSERT, UPDATE, DELETE, ARCHIVE, LOGICAL_EDIT |

Всё кладётся в `AppModel` — корневой контейнер с тремя списками: `entities`, `searches`, ассоциации зашиты внутри сущностей.

## 3. Классификатор сущностей (`EntityClassifier`)

XML-модель содержит **19 объектов**, но не каждый из них — это «нормальная» сущность, которую можно тестировать как отдельную страницу. Классификатор раскладывает их на **3 типа**:

### PRIMARY — основная бизнес-сущность
Главные объекты: ГСК/ОГСК, Совещание, Должностное лицо, Должностные лица и т.п. У них есть собственный пункт меню, собственный поиск с параметрами, собственные операции CRUD. **Тестируются как отдельные классы**.

**Правило:** не CHILD и не REFERENCE_DICTIONARY — значит PRIMARY (по остаточному принципу).

### CHILD — дочерняя сущность (таб-грид у родителя)
Например: «История ГСК/ОГСК» — это таб внутри карточки ГСК/ОГСК, у неё нет своего пункта меню. Самостоятельно не открыть, можно только зайти в родителя и переключить вкладку.

**Правило:** имя сущности по корням слов совпадает с именем `Properties[stereoType="Grid"]` внутри ДРУГОЙ сущности, И у этой сущности нет своих CRUD-операций.

**Стемминг по корням:** «История ГСК/ОГСК» → «истор гск огск» (отбрасываем последние 2 символа каждого слова длиннее 3 символов). Так «Должностное лицо» матчится с «Должностные лица» (учёт русских склонений).

### REFERENCE_DICTIONARY — справочник-перечисление
Например: «Справочник Да/Нет», «Улица», «Район». Это значения, которые выбираются через FK-пикер из другой формы. У них есть только поиск pick-one без параметров.

**Правило (две альтернативы):**
- `featureName` начинается на `V_S_` (системный префикс справочника), ИЛИ
- все связанные `Search` имеют пустой `params` И результат состоит только из служебных полей `SearchKey + SearchName`.

### Результат на типовой XML

```
8 PRIMARY      → 8 тест-классов
5 CHILD        → 0 классов (тестируются как табы родителя)
6 REFERENCE    → 0 классов (тестируются как FK-пикеры)
```

Файл `target/entity-classification.csv` фиксирует решение по каждой сущности с обоснованием.

## 4. Генератор (`TestGenerator`)

Для каждой PRIMARY-сущности создаются **два файла**:

### PageObject (`<Entity>Page.java`)
Класс-обёртка над страницей с методами:
- `fill<Field>(value)` — заполнить поле
- `read<Field>()` — прочитать значение
- `isFieldDisplayed(displayName, attrName)` — есть ли поле на форме
- `hasValidationErrors()`, `fieldHasError(name)` — есть ли подсветки ошибок
- `fillAllFields()`, `fillRequiredFields()` — массовое заполнение

### TestClass (`<Entity>Test.java`)
Сам тестовый класс. Расширяет общий `BaseTest`, переопределяет `entityName()` (возвращает русское имя сущности для меню). Содержит набор `@Test`-методов в зависимости от **уровня покрытия**.

Плюс общие файлы (один раз на проект): `BaseTest.java` (вся логика навигации, ожиданий, скриншотов), `SharedDriver.java` (один Chrome на класс), `TestData.java` (URL, логин, имя подсистемы).

## 5. Уровни покрытия и какие тесты генерятся

| Уровень | Что добавляется | Сколько тестов на класс |
|---|---|---|
| **smoke** | `testFieldsPresent` (просто что форма открылась и есть хотя бы одно поле) | 1 |
| **basic** | + `testSearch[N]` (один тест на каждый поиск из XML), + `testGrid<Tab>` (по каждой таб-вкладке) | 4–7 |
| **full** | + `testCreate`, `testUpdate`, `testDelete`, `testLogicalEdit`, `testArchive`, `testRequiredFieldValidation`, `testPartialRequiredFieldValidation`, `testCreateOnlyRequired`, `testMaskedFieldInput`, `testSearchEmpty[N]` | 13–15 |

### Что каждый тест делает

| Тест | Действие | Что проверяет |
|---|---|---|
| `testFieldsPresent` | Открыть сущность по меню «Найти», запустить дефолтный поиск | На странице видны поля XML-модели (хотя бы одно) |
| `testSearch[N]` | Открыть форму поиска, заполнить параметры, нажать «Готово» | Запрос отработал без ошибок; видны строки в результате |
| `testSearchEmpty[N]` | То же, но с заведомо мусорным значением | 0 строк в результате (фильтр сработал) |
| `testGrid<Tab>` | Открыть карточку записи, переключиться на вкладку | Вкладка открылась, видны её колонки |
| `testCreate` | Открыть «Добавить», заполнить ВСЕ поля, проштамповать первое строковое поле уникальным маркером `AT<nanos>`, «Готово» | Маркер появился в гриде; число строк не уменьшилось |
| `testUpdate` | Выделить первую запись, изменить строковое поле на `Upd<nanos>`, «Готово», перечитать | Новое значение читается либо из карточки, либо из грида |
| `testDelete` | Выделить первую запись (запомнить её текст), «Удалить» | Строка пропала из грида (либо число строк строго уменьшилось) |
| `testArchive` | Аналогично, но действие — «в Архив» | То же, что для delete |
| `testLogicalEdit` | Выделить, «Лог. изменить» | Действие отработало без ошибок |
| `testRequiredFieldValidation` | Открыть «Добавить», очистить форму, «Готово» с пустыми полями | Диалог остался открыт ИЛИ показаны ошибки валидации |
| `testPartialRequiredFieldValidation` | То же, но заполнено только первое обязательное поле | Диалог остался открыт |
| `testCreateOnlyRequired` | Заполнить только обязательные поля, «Готово» | Создание прошло без ошибок |
| `testMaskedFieldInput` | Открыть «Добавить», заполнить замаскированные поля сгенерированными значениями | Значение в форме соответствует маске (через regex) |

## 6. Навигация по меню (E3Core / ExtJS)

Меню E3Core — каскадное: верхняя панель → подсистема → пункт сущности → подпункт действия («Найти», «Добавить», «Изменить» и т.п.). Решается **рекурсивным спуском** `descendMenu` с такими тонкостями:

### 6.1. Стемминг по корням слов
В XML сущность называется «Должностное лицо», а в меню — «Должностные лица». XPath строится через `entityStemPredicate`: каждое слово укорачивается на 2 символа, формируется `contains(text(),'Должностн') and contains(text(),'ли')`. Срабатывает на оба варианта.

### 6.2. Каскад из 4 стратегий клика (`tryClickAllWays`)
ExtJS-меню иногда игнорируют простой `click()`. Перебираем 4 способа подряд до первого успешного:
1. Стандартный `WebElement.click()`
2. Через `Actions.click()`
3. Эмуляция пары `mousedown` + `mouseup` через JavaScript
4. Прямой `JavascriptExecutor.click()`

### 6.3. Повторный поиск меню (`clickEntityMenuItem`)
В отличие от хрупкого `menuAction` (точное `contains(text(),'имя')`), `clickEntityMenuItem` использует стемминг + каскад кликов. Список действий передаётся параметром: пробуем «Изменить» → «Редактировать» → «Открыть» → «Просмотр» → «Карточка» → «Свойства» → «Подробнее» → «Просмотреть», пока что-то не сработает (разные сборки E3Core называют действие по-разному).

### 6.4. Self-healing открытия дерева поисков
Если дерево поисков «по параметрам» закрыто — `openSearch` сначала повторно вызывает `clickEntityMenuItem(entityName, "Найти")`, переоткрывая дерево, потом ищет узел.

## 7. Заполнение форм — PropertyGrid

Формы поиска и редактирования в E3Core — это **PropertyGrid** (двухколоночная таблица «Наименование / Значение»). Правые ячейки **не являются обычными `<input>`** — они активируются как inline-редактор только при клике.

### Как заполняем (`fillPropertyGridCell`)
1. Найти строку, где левая ячейка содержит текст метки (например, «Наименование ГСК/ОГСК» — с обрезанием маркера обязательности `*`).
2. **Двойной клик** по правой ячейке (одного не хватает — первый выделяет строку, второй активирует редактор).
3. В появившемся inline-редакторе очистить, ввести значение.
4. Нажать `Tab` для коммита.

### Fallback-стратегии fillSearchParam
Если PropertyGrid не сработал, пробуем (по убыванию надёжности):
- `[name='X']` или `[id='X']` — обычный HTML
- `[id^='X-']` — ExtJS-суффикс
- по `<label>` с русским title параметра — там, где разметка ближе к стандартной форме

Логируется какая стратегия сработала: `fillSearchParam 'GBS_NAME' = 'Test_GBS_NAME' (via: PropertyGrid cell)`.

## 8. Кнопка submit поиска — три варианта подряд

В разных контекстах E3Core кнопка запуска поиска называется по-разному. `executeSearch` пробует подряд:
1. **«Готово»** — самый частый случай (форма поиска)
2. **«Выполнить поиск»** — отдельный результат-грид
3. **«Найти»** — старая разметка

Берётся первая видимая и доступная.

## 9. Параметры поиска — что отправляем

Для каждого `SearchParam` из XML формируется значение:

| Условие | Значение |
|---|---|
| `searchGuid` задан (FK-параметр) | **Пропускаем** — это пикер, автозаполнение невозможно |
| Маска формата `99.99.9999` | Сегодняшняя дата `dd.MM.yyyy` |
| Маска формата `99.99.9999 99:99` | Сегодняшняя дата + `12:00` |
| Другая маска | Цифры 1,2,3…0 по позициям мaski |
| `valueType="integer/decimal/number"` | Случайное число 100–999 |
| `valueType="date"` / `"datetime"` | Сегодня |
| Прочие | `"Test_" + имяПараметра` |

Перед заполнением логируется блок параметров (потом парсер вытаскивает его в отчёт):

```
=== Search params for 'по параметрам' ===
  GBS_NAME = 'Test_GBS_NAME'
  INN = '123456789012'
  DATE_BEGIN_OT = '19.05.2026'
  KEY_TYPE_SOCIETY = '<FK-lookup 'Тип ГСК/ОГСК' — skipped>'
==========================================
```

## 10. Скриншоты — фотолетопись прогона

В `BaseTest` поле `stepCounter` сбрасывается в `@BeforeEach`. Метод `shot(step)` сохраняет PNG с именем:

```
<EntityClass>_<testMethod>_NN_<stepName>_<status>.png
GSKOGSK_testCreate_03_filled_OK.png
```

В каждом тесте вызывается **5–8 раз** в ключевых точках:
- `start` — начальное состояние
- `dialog_opened` — открыли «Добавить»
- `all_fields_filled` — заполнили
- `marker_applied` — проштамповали уникальный маркер
- `after_save` — после «Готово»
- `marker_in_grid` / `final_grid` — результат
- финал в `@AfterEach`

Папка `target/screenshots/` после прогона читается как **покадровая хроника прогона**.

## 11. Отчёты

### `target/run-report.html` — главный артефакт
Автономный HTML (не нужен сервер) — открывается локально. Содержит:
- Шапку (дата, длительность, имя XML, URL стенда)
- Сводку: `Всего N | ✓ X | ✗ Y | ⏭ Z`
- Раскрывающиеся блоки по тест-классам и тест-методам
- Для каждого метода: статус, длительность, фотолента, таблица параметров поиска, таблица таймингов шагов, сообщение об ошибке, сворачиваемый stdout

### `target/run-report.csv` — для Excel
Одна строка на тест-метод: класс, тест, статус, длительность, параметры поиска, число шагов, число скриншотов, сообщение об ошибке.

### `autotestgen.db` — SQLite-история
Таблицы `test_run` (одна строка на прогон) и `test_case` (одна строка на тест в прогоне). Хранится между запусками, доступно через GUI «История».

### Парсеры в `TestRunner`
- `extractSearchParams(stdout)` — вытаскивает блоки `=== Search params for 'X' ===`
- `extractStepTimings(stdout)` — вытаскивает строки `[step] name: NNNms`
- `linkScreenshots(dir)` — привязывает PNG к тест-методам по имени файла

## 12. Стабильность и скорость

### Условные ожидания вместо blind sleep
Раньше после каждого клика стоял `Thread.sleep(1000-2000)`. Теперь:
- `waitForDialog()` / `waitForDialogClose()` — ждут открытия/закрытия `.x-window`
- `waitForGridSettle()` — ждёт пока число видимых строк перестанет меняться 500мс подряд
- `waitUntil(condition, sec, desc)` — универсальный poll

На быстром стенде ожидание возвращается за 100–200мс вместо безусловной секунды — выигрыш по времени ~40%.

### Тайминги шагов
`step(name, () -> body)` оборачивает действие, печатает `[step] name: NNNms`. Эти строки парсятся обратно в отчёт — получается мини-гантт каждого теста.

### Изоляция Chrome
В `pom.xml` сгенерированного проекта `forkCount=1` — один Chrome на весь прогон, тесты внутри класса последовательны (важно для CRUD-цепочки testCreate → testUpdate → testDelete).

### Кэширование навигации
`cachedNavigationOk` в BaseTest: если первая навигация в `@BeforeEach` провалилась, последующие тесты класса не пытаются её повторить, сразу помечаются как `Assumptions.assumeTrue(false)` → SKIP с понятной причиной.

## 13. Почему «сущностей много», а тестов мало

В типовой XML: **19 сущностей**, но генерируются тесты только для **8 PRIMARY**. Остальные 11:
- **5 CHILD** — реально тестируются как табы внутри карточек родителя (`testGridИстория` внутри `GSKOGSKTest`), отдельных классов не нужно.
- **6 REFERENCE** — справочники-перечисления (Да/Нет, Тип ГСК, Улица, Район…), они нигде не выбираются как самостоятельная страница, только через FK-пикер.

Итого: классификатор фильтрует **11 «фантомных» тестов**, которые в первой версии системы стабильно проваливались с сообщением «Could not navigate to entity».

В CSV `entity-classification.csv` каждое решение задокументировано:

```
kind,                 entity,                          reason
PRIMARY,              ГСК/ОГСК,                       has menu entry, CRUD and own searches
CHILD,                История ГСК/ОГСК,               tab/grid 'История ГСК/ОГСК' inside 'ГСК/ОГСК'
REFERENCE_DICTIONARY, Справочник Да/Нет,              featureName starts with V_S_
REFERENCE_DICTIONARY, Улица,                          all searches are pick-one (no params)
```
